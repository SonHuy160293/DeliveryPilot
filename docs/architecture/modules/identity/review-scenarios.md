## Scenario matrix

| Ref | Given / action | Expected outcome and integrity boundary | Authority / design state |
|---|---|---|---|
| ID-01 | Alice registers without joining an organization. | Existing registration creates active User+credential; EmailVerifiedAt remains null. No membership, workspace or automatic login. | Implemented baseline and I/D-001–003; no test run here. |
| ID-02 | Alice has memberships in organizations A and B. | One global User; distinct organization memberships/assignments. A roles cannot authorize B actions. | W/Q1–Q5; combined local relationships under SCOPE-01. |
| ID-03 | New workspace creation fails while establishing initial Owner. | Proposed transaction rolls back Organization, membership, Owner assignment and material audit/outbox together. No orphaned live workspace. | W/Q1 establishes creator Owner; atomic persistence is proposed Stage C boundary. |
| OWN-01 | Alice and Bob both hold Owner responsibility. | Both can be Owners. The model cannot require exactly one exclusive OwnerId. | User-selected OWN-01. |
| OWN-02 | Alice and Bob concurrently remove/demote their own Owner assignments. | Normal changes cannot leave no active eligible Owner; serialize through a common organization invariant boundary. Independent per-member checks are insufficient. | Owner protection selected; OWN-02 protocol proposed. |
| OWN-03 | Sole eligible Owner is compromised/suspended. | Deny that account immediately; block privileged changes with no eligible Owner and no auto-promotion. Ordinary reads still require current grants; operator recovery is separately scoped. | OWN-08/U19 selected containment; production recovery operating review deferred. |
| OWN-04 | Alice transfers responsibility to Carol while Bob remains Owner. | Carol first accepts additional ownership; Alice separately steps down. Other roles remain or Member is assigned if none remain; Bob stays Owner. | OWN-07/U15 and AUTHZ-08/U12 selected; no automatic swap. |
| OWN-05 | Alice, an existing Owner, nominates existing member Carol as an additional Owner. | Nomination grants nothing; Carol must explicitly accept before receiving additional ownership, leaving existing Owners in place. | User-selected OWN-05/06/U9/U15 selects seven-day active-sponsor/nominee lifecycle and cancellation/decline. Persistence is task design. |
| CREATE-01 | A registered person creates a workspace with a trimmed nonblank name of at most 160 characters; another workspace has the same name. | Name-only creation is eligible without slug; duplicate names are allowed. Invalid/over-limit names do not create a workspace. | User-selected CREATE-01/U9; uncertain-response retry semantics remain feature OD-02. |
| MEM-01 | Member leaves organization A and later rejoins. | Same durable membership identity and retained transition history; no second competing relationship row for A/User. | User-selected MEM-01. |
| MEM-02 | Former Admin rejoins as an ordinary member. | Previous Admin grants stay ineffective; newly authorized current roles govern. Reactivating membership alone must not restore old access. | User-selected MEM-02. |
| MEM-03 | Temporary suspension/restoration operation is requested. | No command/UI in this release; any already-suspended state denies access/joining and invitation cannot bypass it. | MEM-05/U18 explicit release exclusion, not an unanswered in-scope branch. |
| AUTHZ-01 | Alice receives two organization roles with overlapping permissions. | Combine allowed permissions within A only; duplicate permission collapses. Suspension and mandatory restrictions still deny. | User-selected AUTHZ-01; no executed behavior test claimed. |
| AUTHZ-02 | A custom-role editor adds a sensitive permission to a role already assigned to them. | Require role-management authority plus held, catalog-delegable organization permissions; evaluate affected holders. Built-in definition edits remain prohibited. | User-selected AUTHZ-03 ceiling and AUTHZ-02 built-in protection. |
| AUTHZ-03 | A role from organization B is assigned to a membership in A. | Reject with same-organization local integrity; caller authorization is still required even for valid local references. | Proposed composite local constraint and policy. |
| AUTHZ-04 | Customer attempts to edit built-in Owner, Admin or Member role definitions. | Reject the definition edit; customize access using customer-defined roles under the selected delegation policy. System-controlled version upgrades remain a separate design concern. | User-selected AUTHZ-02; Origin/TemplateVersion columns proposed, upgrade policy open. |
| AUTHZ-05 | Alice is neither Owner nor Admin but has explicitly delegated ordinary role management. | Eligible only within her held, catalog-delegable organization permissions; protected Owner operations/platform privilege remain excluded. | User-selected AUTHZ-05 eligibility and AUTHZ-03 ceiling. |
| INV-01 | An active but unverified User presents an invitation addressed to a different person. | Deny despite active status: both valid single-use link proof and current signed-in primary-email match are required. No separate fresh email code; registration remains unverified. | User-selected INV-01; address-history/global-verification policy INV-03 remains open. |
| INV-02 | Two inviters issue conflicting offers for A and the same normalized address. | At most one pending offer regardless of role combination; duplicate/conflict/reissue handling cannot stack hidden offers. | User-selected INV-02 uniqueness; exact conflict workflow remains proposed. |
| INV-03 | Acceptance races cancellation, resend or expiry. | One conditional state/version winner; no consumed proof without corresponding authorized membership/grants and audit. Old rotated proof cannot redeem. | INV-02 uniqueness selected; local transaction/concurrency protocol proposed. |
| INV-04 | Same subject retries successful acceptance after uncertain response. | Already-accepted outcome with current permitted information only; no new grant or restored access after removal/suspension. Wrong subjects receive no restricted outcome. | INV-08/U16 selected replay; exact transport is task design. |
| INV-05 | Offered role gains or loses permissions before acceptance. | Compare OfferedPermissionSetVersion; close old offer and atomically create linked replacement with fresh proof/snapshot. Mere sponsor reapproval is insufficient. | AUTHZ-04 selected; physical representation PHY-02 proposed. |
| INV-06 | An offer targets active, removed or suspended membership. | Active uses role management; removed may rejoin on fresh authorized offer with durable identity/fresh grants; suspended joining is denied. | MEM-04/U14 selected; suspension/restoration commands deferred in U18. |
| INV-07 | Expired invitation remains Pending because cleanup is delayed. | Deadline still denies redemption. New issue handles stale Pending state consistently while preserving one pending organization/recipient offer. | INV-02 uniqueness selected; expiry transition mechanics proposed. |
| INV-08 | Delivery fails after offer persistence. | Offer stays pending with visible delivery status; automatic retry uses only current valid proof and never extends expiry. Explicit Resend alone rotates proof/restarts seven days. | INV-10/U16 selected; provider scheduling is task design. |
| INV-09 | Primary email no longer matches offered address. | Reject preview/accept/decline under old proof; no alias/history override or automatic forwarding. A different address needs a separately authorized matching-address offer. | INV-01/09 selected; account email-change workflow deferred. |
| INV-10 | Matching signed-in, active User redeems an unchanged, valid invitation link. | Recipient proof is satisfied without a separate code or existing EmailVerifiedAt. Commit invitation consumption and authorized membership/grants atomically under the selected acceptance rules. | INV-01 selected; remaining acceptance/state details still proposed. |
| INV-11 | Sponsor loses delegation authority while offered role permissions remain unchanged. | Block acceptance; a currently authorized inviter must reissue. Link possession does not preserve lost delegation authority. | User-selected INV-04/U10; distinct from AUTHZ-04 permission drift. |
| INV-12 | Recipient presents proof exactly at or after seven days from issue while cleanup is delayed. | Deadline denies acceptance even if status still reads Pending. | INV-05/U10 selects seven-day lifetime; expiry processing representation remains proposed. |
| INV-13 | An authorized unchanged offer is resent at T with new proof. | Old proof is unusable; deadline restarts at T plus seven days. Resend does not silently change offered permissions. | INV-06/U10 selected; INV-07/08/09/10 and U14/U16/U21 select terminal-offer, duplicate/replay and delivery outcomes. |
| PLATFORM-01 | Platform operator has no organization membership. | Separate platform assignment can identify authority independently of memberships; current operational enablement remains deferred. | SCOPE-02 selected; PLAT lifecycle details open. |
| PLATFORM-02 | Organization Admin attempts to assign System Administrator through organization role API. | Reject regardless of organization ownership; platform role definitions/assignments are system-controlled. | Selected boundary; PLAT-01 procedure proposed. |
| PLATFORM-03 | System Administrator asks for a private customer requirement. | Platform assignment alone provides no project/share/reviewer grant; resource owner denies. | Selected no-content-bypass scope. |
| PLATFORM-04 | Platform authority is revoked while User is a legitimate member of organization A. | Platform access ends; A membership continues to be evaluated independently. No automatic global user deletion. | PLAT-03 proposed. |
| PLATFORM-05 | Last usable platform administrator expires or is compromised. | Normal continuity guard plus an independently reviewed emergency route required; MFA/recovery deferral cannot be hidden by a row count. | PLAT-02/03 unresolved; prevents enabling privileged operations. |
| ACCESS-01 | User is suspended after recording a historical customer approval. | New authentication/authorization denies; existing actor and immutable decision attribution remain in the resource owner. No cascade into approvals. | Current account check plus proposed retention DATA-02. |
| ACCESS-02 | Membership/role reduction commits while access JWT remains valid. | New decisions deny revoked powers; identity token alone is no workspace grant. Admitted reads may finish; Identity mutations recheck before commit. | ACCESS-02/U19 selected boundary. |
| ACCESS-03 | Revocation commits while queued/external work is pending. | Reauthorize queued work at execution; required facts unavailable fails closed. Resource owners must implement explicit contracts without a claimed cross-database atomicity guarantee. | ACCESS-02/U19 selected contract; integration is task design. |
| BOUNDARY-01 | Organization Owner tries to read a project they have not joined. | Organization role alone does not grant project-content visibility; Project decides actual access. | W/Q2–Q6 and SCOPE-04. |
| BOUNDARY-02 | External client joins only a shared Project review. | Global User may have zero OrganizationMembership rows; Project/resource owner supplies narrow participation/share/reviewer authority. | W/Q3 and SCOPE-04. |
| BOUNDARY-03 | External module queries Users or Memberships through Identity DbContext. | Design rejects cross-module database access; use minimal authorized public contracts. Co-hosting does not change ownership. | Repository architecture constraint. |
| COLUMNS-01 | Same member receives the same role after a prior grant ended. | Keep assignment Id and pair uniqueness; increment GrantVersion and Version. Old grant facts/reasons remain immutable in audit; update Membership.Version and ordered events in the same local transaction. | AUTHZ-06/DATA-01 selected; proposed columns and transaction protocol. |
| COLUMNS-02 | Two grant/status changes affect the same membership concurrently. | Parent conditional revision serializes committed history; allocate distinct EventOrdinal values within each MembershipVersion. No timestamp-only ordering or duplicate revision/ordinal pair. | Proposed audit/version protocol; no runtime test claimed. |
| COLUMNS-03 | A role's permission set changes and later returns to the original codes. | PermissionSetVersion advances on both changes; old offers still mismatch and require reissue. Snapshot version is not a FK that blocks role updates. | AUTHZ-04 selected; snapshot/counter design proposed. |
| COLUMNS-04 | A platform grant or bootstrap event has no organization/member and no ordinary User actor. | NULL scope/member columns are valid; system/operator ActorKind requires a nonsecret ActorReference. User actor requires ActorUserId. No fabricated User or membership is created. | Proposed platform/audit columns; privileged operations remain deferred. |
| COLUMNS-05 | Audit serializer attempts to store raw invitation secret, TokenVerifier, password hash or request payload. | Reject by event-specific allowlist. Details is a structured object, not a transport dump; snapshots contain registered permission codes only. | Proposed payload/security contract. |
| COLUMNS-06 | Invitation accepts, declines or expires. | Pending closure fields are NULL. Accepted/declined have ClosedAt and ClosedByUserId; accepted closure identifies recipient membership by OrganizationId/UserId. System expiry closes without a fake human actor. | INV-01 selected; lifecycle column/check proposal. |
| COLUMNS-07 | Required success-audit persistence fails. | Protected mutation also fails, with no false success evidence. Denials emit separate minimal telemetry; durable denied-attempt history is not included. | AUDIT-01/U20 selected business consistency; exact transaction design proposed. |

## Traceability and completeness checks

- Every proposed entity/attribute concept has a purpose, decision reference or implemented source; diagram relationships match dictionary cardinality and ownership.
- Selected CREATE-01/OWN-01/OWN-05/MEM-01/MEM-02/AUTHZ-01–06/INV-01/INV-02/INV-04/INV-05/INV-06/DATA-01/DATA-03 are applied consistently; other open defaults are not recorded as answered.
- Local User FKs appear as permitted by combined Identity ownership. Project/Delivery references stay external and scalar.
- Existing physical diagram fields exactly match mapped business columns; candidate columns are never presented as implemented.
- Each invariant has a database, domain/application or caller-authorization enforcement owner. Cross-row continuity and cross-database races are explicitly distinguished.
- Proposed new table columns agree between dictionary and physical diagrams. Policy, privilege readiness, retention and operational review still gate production finalization; typed draft columns do not establish application implementation.
- Original discovery links and canonical artifact IDs remain valid; no approval evidence or application implementation status is changed by these design notes.
