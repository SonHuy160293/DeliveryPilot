## Round 2: organization authorization

W/Q5 confirms built-in/custom roles and constrained delegation. AUTHZ-01–06 are selected with U4/U5/U7 provenance. For ordinary organization grants, require explicit role-management authority, target permissions within the actor's current effective permission set, and catalog delegability. Owner assignment uses its protected workflow; platform codes never enter this path. AUTHZ-07–12/U11–U17 select readers, protected targets, capability defaults, role inputs/retirement and stale-edit/upgrade policy. Exact registered permission-code representation and reviewed upgrade implementation are task design, not additional grant tables.

## Aggregate and transaction proposals

These are candidate consistency boundaries for Stage C review, not a single aggregate spanning the entire database.

| Operation | Local transaction and invariants | External behavior |
|---|---|---|
| Registration | Preserve existing User+PasswordCredential persistence and normalized-email guard. | No organization, token issuance or verification message automatically created. |
| Workspace creation | Organization+creator membership+initial Owner assignment+material audit/outbox. Initial Owner follows the authorized creation rule, not ordinary grantor delegation. | Publish committed outcome if needed; no Project creation implied. |
| Organization invitation acceptance | Serialize invitation status/version and intent; consume proof, activate membership, assign newly authorized roles, write audit/outbox. Protect existing suspended/removed relationships from stale offers. | Notification delivery is retriable outside the transaction. |
| Owner transfer/removal | Shared Organization guard plus affected memberships/assignments and evidence. Account suspension may affect owners across organizations; review that path too. | Project does not receive implicit administrator changes. |
| Role definition/assignment | Current delegation check, local scoped integrity, role/member security version and audit/outbox. | Events invalidate derived access; authoritative checks remain necessary. |
| Platform grant/revoke | Protected platform authority/continuity guard, target account eligibility, assignment and durable audit. | Customer memberships unchanged; future elevation invalidation needs an explicit contract. |

## Minimum external contracts

Existing [UserIntegrationDto](../../../../src/Contracts/DeliveryPilot.Identity.Contracts/Users/UserIntegrationDto.cs) and [Users controller](../../../../src/Modules/DeliveryPilot.Identity/DeliveryPilot.Identity.API/Controllers/UsersController.cs) provide the current protected integration lookup. Authentication context validation is currently an Identity-host foundation. The following capabilities are proposed; no new route, interface or broker message is implemented here.

| Capability | Inputs / outputs at design level | Enforcement owner |
|---|---|---|
| Account/session eligibility | Authenticated User and session IDs → active/invalid/unavailable result, with minimal necessary facts. | Authentication; caller fails closed on unavailable required facts. |
| Organization eligibility | Actual OrganizationId and authenticated UserId → lifecycle, membership state and relevant version. | Identity; caller cannot enumerate arbitrary memberships. |
| Scoped authorization/delegation | Actor, organization, action and proposed grant → authorized/denied with scoped policy evidence. | Identity for organization operations; Project/Delivery still decides its own resource actions. |
| Minimal identity projection | Authorized lookup by stable ID → existing permitted display/status fields. | Identity; do not expose email/credential/session material broadly. |
| Access-change propagation | Committed source event identity, aggregate version, affected scope/subject and change kind. | Identity outbox; consumers deduplicate, preserve history and reject stale state overwrites. |

Combining Authentication and Organization removes an inter-module dependency between them. It does not make calls to Project, Notification, or future Delivery databases atomic. Event propagation supports projections and reconciliation; it is not the sole access-revocation authority.
