# FR-DP-025-009 — Confirm and remove a client organization link

**Provenance:** Drafted 2026-11-09 with `dp-feature-engineer` from the roadmap, requirements, workflow discovery and [ADR-001](../../../architecture/adr-001-delivery-module-placement.md). Business choices marked **User-selected** were made by the user in the joint feature review on 2026-11-09 (see the decision record in [feature.md](../feature.md)). `ready` records internal completeness review for task planning, not client approval; `approval_ref` stays null and nothing here is implemented.

## Requirement statement
The system shall let an Owner or Admin of an existing Identity organization confirm a valid link code while acting in that organization, storing that organization's ID as the engagement's `ClientOrganizationId`, and let either side remove a confirmed link; the link never grants access.

## Preconditions and trigger
A signed-in user acting in organization C enters a code. Projects asks Identity (organization check with the user's session, uncached) whether the user is an active Owner or Admin of C.

## Main behavior
With a valid, unexpired, unused code: show a confirmation preview (engagement name and client display name only), then on confirmation set `ClientOrganizationId` = C, consume the code, record confirmer user ID, organization and UTC time. Owners/Admins of C can list engagements linked to C (engagement name and client display name only) and remove a link; vendor `organization.engagements.manage` holders can also remove it. Removal is attributable, keeps history and is allowed while the engagement is Closed. Linking or removal changes no project participation, guest grant or membership.

## Validation, business rules and authorization
- C must not be the engagement's own vendor workspace.
- **User-selected (OQ-025-13, 2026-11-10):** either side may remove a confirmed link on a Closed engagement; confirming a link still requires an Active engagement.
- Uses Identity's existing organization check (IsOwner/IsAdmin); no new Identity contract is required.
- Invalid, expired or used codes give one generic failure; failed attempts are rate limited per user (limits are task configuration).
- Scalar ID only, no cross-database FK (D-08); decisions attributable (NFR-003).

## Failure and edge cases
- User is a plain Member of C, or membership/session no longer valid: denied.
- Code expired, used, invalidated or engagement Closed: generic failure.
- C equals the vendor workspace: rejected.
- Identity unavailable: fail closed.

## Verification criteria
- An Owner of C confirms; the vendor sees C linked; no member of C gains vendor project access.
- A Member of C who is neither Owner nor Admin cannot confirm.
- Guessing codes yields only generic failures and hits the rate limit.
- After removal by either side the link is gone and history remains.
- A confirmed link on a Closed engagement can be removed by an Owner or Admin of C and by a vendor manage holder.

Criteria are scenarios for task planning, not executed tests.
