# UR-DP-025-005 — Link an engagement to the client's own workspace with the client's consent

**Provenance:** Drafted 2026-11-09 with `dp-feature-engineer` from the roadmap, requirements, workflow discovery and [ADR-001](../../../architecture/adr-001-delivery-module-placement.md). Business choices marked **User-selected** were made by the user in the joint feature review on 2026-11-09 (see the decision record in [feature.md](../feature.md)). `ready` records internal completeness review for task planning, not client approval; `approval_ref` stays null and nothing here is implemented.

## Problem and context
Some clients also use DeliveryPilot in their own workspace. Vendors want to recognize that the engagement's client is that workspace, for future cross-workspace experiences, but the vendor must never create or own the client's workspace, and the link must not leak access in either direction (ADR-001 D-09).

## User need
As a vendor engagement manager, I need to give the client a one-time code, and as an Owner or Admin of the client organization I need to confirm the link with that code, so that both sides agree the link is genuine without exposing organization lists.

## Business value and observable outcome
A linked engagement shows a confirmed client organization; without confirmation there is no link. The link grants no access to vendor projects and does not replace guest grants (D-09).

## Scope, constraints and exceptions
- Optional; engagements work fully without a link.
- **User-selected (OQ-025-10):** vendor-generated single-use code, 7-day expiry, confirmed by an Owner or Admin of the client organization through Identity's existing organization check; either side may remove the link.
- The client organization must already exist in Identity, created by the client's own user (creator-is-Owner rule).
- Project co-ownership remains out of MVP.

## Evidence and validation
**Accepted architecture decision:** ADR-001 D-09. **User-selected:** link-code flow (2026-11-09).
