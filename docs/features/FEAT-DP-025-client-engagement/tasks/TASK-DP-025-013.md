# TASK-DP-025-013 — Publish engagement routes through the Gateway

## Objective and source contract
Expose the engagement API through the YARP Gateway with an explicit allowlist and run the engagement journey end to end. Sources: [ADR-001](../../../architecture/adr-001-delivery-module-placement.md) §5 (Gateway row); [FR-DP-025-001](../fr/FR-DP-025-001.md), [FR-DP-025-006](../fr/FR-DP-025-006.md), [FR-DP-025-009](../fr/FR-DP-025-009.md); [US-DP-025-001](../us/US-DP-025-001.md), [US-DP-025-006](../us/US-DP-025-006.md), [US-DP-025-008](../us/US-DP-025-008.md). All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

## Codebase evidence
Reviewed 2026-11-12 against current source and the completed link flow. `proxy.json` has 35 explicit Identity/Notification routes and no Projects cluster. The four Projects controllers supply 21 method/path pairs after task 004: engagement collection/detail/history/value/state/code/removal, contact and milestone mutations, and client link preview/confirm/list/removal. They use GUID route constraints and 16,384-byte request ceilings. Existing Gateway rig tests load production proxy configuration, but the organization inventory assumes all non-auth routes belong to Identity; scope that inventory by cluster when adding Projects.

`GatewayRequestMiddleware` needs the Projects organization prefix in its no-store handling. CORS already allows GET/POST/PUT, Authorization, Content-Type and Idempotency-Key and exposes Retry-After. The Gateway server Compose model needs a projects-api destination override in addition to the local fallback cluster address. `Test-GatewayDeployment.ps1` requires an explicitly disposable Development stack and currently verifies Identity/Notification only; extend its inventory, internal-alias checks and real-session engagement journey. `Test-ProjectsDeployment.ps1` supplies existing registration/workspace helpers. No project content routes are added. Requirements remain `ready` with `approval_ref: null`.

## Scope and dependencies
**In scope:** the `projects` cluster; one allowlisted route per engagement endpoint that exists when this task starts; CORS methods and headers those routes need (including `Idempotency-Key`); `no-store` handling; route tests; the deployed journey check.

**Out of scope:** FEAT-DP-004 routes; the blocked summary tier ([TASK-DP-025-011](TASK-DP-025-011.md)), which adds no route.

**Staged publication (user-selected, 2026-11-10):** this task may publish the implemented engagement functions before TASK-DP-025-011. Publication does not complete FEAT-DP-025: participant summaries and project/administrator visibility remain unmet until TASK-DP-025-011 and its prerequisites are delivered.

**Depends on:** [TASK-DP-025-012](TASK-DP-025-012.md) for a running Projects API, and the API tasks [TASK-DP-025-002](TASK-DP-025-002.md)–[TASK-DP-025-010](TASK-DP-025-010.md). Publish only the routes whose tasks are done; the route list in each task is a proposal, so take the final paths from the controllers in source.

## Behavior and invariants
- Public prefix `/projects/api/v1/...` (proposed, mirroring `/identity/api/v1/...`), forwarded to the Projects API without the prefix.
- Explicit allowlist: no catch-all route. Unlisted paths and methods get the existing Gateway 404/405 responses.
- Route parameters keep GUID constraints; request body limits and timeouts follow the Identity routes.
- Engagement responses are `no-store` at the Gateway as well as at the API.
- The Gateway adds no authorization of its own and does not weaken the Projects API's checks.
- The internal Identity authority endpoints stay unpublished.

## Persistence, events and integrations
None. Correlation ID and trace headers pass through as for the existing clusters (NFR-009).

## Executor handoff
Module `src/Gateway/DeliveryPilot.Gateway` and its tests. No CQRS use case, so `implementation_skill` is null.

## Implementation plan
1. Add the `projects` cluster and the routes to `proxy.json`.
2. Extend the `no-store` prefixes in `GatewayRequestMiddleware`.
3. Add route tests next to `GatewayOrganizationRouteTests`.
4. Extend `scripts/Test-GatewayDeployment.ps1` and run the journey against a local deployment.

## Test matrix
- **Allowlist:** every published engagement route is forwarded to the `projects` cluster; an unlisted Projects path gives 404 and a wrong method gives 405.
- **Constraints:** a non-GUID ID gives 404 at the Gateway.
- **Headers:** CORS preflight allows `Idempotency-Key` and `Authorization` for the configured origin only; responses carry `no-store`.
- **Journey (deployed, local):** create an engagement, read it, edit it, add a milestone and a contact, issue a link code, confirm it from a second organization, remove the link, close and reopen, all through the Gateway with real Identity sessions.
- **Isolation (deployed):** a user of another workspace gets 403 or 404 on every step.
- **Regression:** existing Gateway tests pass.
