# TASK-DP-025-006 — Manage engagement milestones

## Objective and source contract
Let a manage holder add milestones, edit them, move their target date with a reason and change their status, keeping the original date. Sources: [FR-DP-025-004](../fr/FR-DP-025-004.md), [FR-DP-025-010](../fr/FR-DP-025-010.md); [US-DP-025-004](../us/US-DP-025-004.md); OQ-025-05. ## Scope and dependencies
**In scope:** add, edit (name, description), change target date, change status.

**Out of scope:** links from milestones to projects, Sprints, releases or payments; Risk events (ADR-001 D-10, defined when that consumer exists); Change Request gates.

**Depends on:** [TASK-DP-025-002](TASK-DP-025-002.md). It changes the same aggregate and controller as the other engagement mutation tasks, so run them one at a time.

## Behavior and invariants
- The handler first calls `IWorkspaceAuthority.RequireAsync` with `organization.engagements.manage`, uncached. A caller without the code gets 403 before any engagement is loaded, so nothing about the engagement is revealed.
- It then loads the engagement by `(OrganizationId, Id)` with a row lock (`FOR UPDATE`). No row gives 404.
- A Closed engagement gives 409 `Engagement.Closed` and no change (FR-DP-025-007).
- Every accepted change increments `Engagements.Version` and appends exactly one `engagement.EngagementEvents` row in the same transaction, with `ActorUserId`, `ActorOrganizationId`, UTC `OccurredAt`, `Reason`, `Details` (previous and new values) and the resulting `EngagementVersion`.
- A request that changes nothing appends no event and does not change the version.
- The pipeline transaction commits; the handler does not call `SaveChangesAsync`.
- A milestone has name (trimmed, 1–200), optional description (≤2000), `OriginalTargetDate`, `CurrentTargetDate` and status. A new milestone is `Planned` with equal dates.
- Changing `CurrentTargetDate` requires a non-blank reason. `OriginalTargetDate` never changes.
- Transitions: `Planned` → `Achieved` | `Missed` | `Retired`; `Missed` → `Achieved` | `Retired`. `Achieved` and `Retired` are terminal: no edit, date change or status change.
- Edits use the milestone's own `expectedVersion`. The engagement row is still locked and its `Version` incremented, but the engagement version is not compared, so two managers can edit different milestones (planner decision, consistent with ERD convention 6).
- Events: `milestone.added`, `milestone.changed`, `milestone.date-changed`, `milestone.status-changed`, with `SubjectType = Milestone`.
- Retired milestones stay readable.

## API contract (only for API tasks)
- **Route base (proposed, mirrors Identity):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/engagements`. Not exposed through the Gateway until TASK-DP-025-013.
- **Authentication and tenant:** `[Authorize]`. User ID and session ID come from `ICurrentUserProvider` (`CurrentUser.Id`, `CurrentUser.SessionId`). The workspace is the route `organizationId`, confirmed by `IWorkspaceAuthority`; it is never taken from token claims or the body (BR-008).
- **Errors (through `GlobalExceptionHandlingMiddleware`):** 400 `CqrsValidationException`; 401 no valid session; 403 `ForbiddenException` when Identity denies the workspace or the required code is missing; 404 `NotFoundException` for an engagement of another workspace or outside the caller's visibility, with the same response in both cases; 409 `ConflictException`; 503 `ServiceUnavailableException` when Identity cannot answer (fail closed).
- **Routes (proposed):**
  - `POST .../engagements/{engagementId:guid}/milestones`;
  - `PUT .../milestones/{milestoneId:guid}` (name, description);
  - `POST .../milestones/{milestoneId:guid}/change-date`;
  - `POST .../milestones/{milestoneId:guid}/change-status`.
- **Bodies:** add: `name`, `description`, `targetDate`. Edit: `expectedVersion`, `name`, `description`. Change date: `expectedVersion`, `targetDate`, `reason` (required). Change status: `expectedVersion`, `status`, `reason` (optional). `POST` add returns 201.
- **Success:** 200 with the updated resource and its new `version`.
- **Errors:** 400 for a blank name, missing date or missing reason; 404 for a milestone not in this engagement; 409 `Milestone.VersionConflict`, `Milestone.InvalidTransition` or a Closed engagement.

## Test matrix
- **Add:** identical original and current dates, status `Planned`, one event.
- **Shift date:** both dates, reason, actor and UTC time are visible in the detail read and history; a missing reason gives 400.
- **Transitions:** every allowed transition succeeds; `Achieved` → `Planned`, `Retired` → anything and edits of terminal milestones give 409.
- **Concurrency:** stale milestone version gives 409; two different milestones edited in parallel both succeed.
- **Ownership:** a milestone ID of another engagement gives 404.
- **Authorization:** the engagement creator without the manage code gets 403; Identity unavailable gives 503; nothing changes.
- **Cross-tenant:** an engagement ID of another workspace gives 404.
- **Closed:** every route of this task gives 409 on a Closed engagement.
