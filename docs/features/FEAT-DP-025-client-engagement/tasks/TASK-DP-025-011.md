## Behavior and invariants
- **Tenant filter first, then tier** (ADR-001 D-07). Every query starts with `OrganizationId`.
- **Full tier (unchanged):** read-all or manage, or `CreatedByUserId` of that engagement.
- **Summary tier (new):** the caller has a participation with `Kind = Member` and `Status = Active` in a project with the same `OrganizationId` whose `EngagementId` is this engagement. It is evaluated in the same query on every request, so a participant who is removed or leaves loses it on the next request.
- **Both tiers:** full wins.
- **No tier:** detail and history give 404 `Engagement.NotFound`, the same response as for a non-existent engagement; the list leaves the engagement out.
- **History stays full-tier only.** A summary-tier caller gets 404 from history.
- **Guests** never see engagement records. Identity denies them the workspace (403), and the `Kind = Member` filter would exclude them even if they got through.
- **Summary content:** engagement ID, client display name, engagement name, agreement reference, status, milestones (the existing milestone view), version. Nothing else: no contract value, currency, effort, contacts, client-link state, link-code state, creator, history or projects.
- **Projects section (full tier only):** every project under the engagement in the caller's workspace, ordered by `CreatedAt` then `Id`. Each has `id`, `name`, `status` and `administrators`. Administrators are participants with `Status = Active` holding a `ProjectAdministrator` grant with `RevokedAt IS NULL`, each as `{ userId, displayName }`, ordered by `displayName` then `userId`. No other project field.
- **Names:**
  - Resolved per request through the new user directory; never stored or cached (PRJ-12).
  - All administrator IDs in one response are deduplicated and sent in batches of at most 100, one call per batch.
  - A user Identity leaves out gets `displayName: null`.
  - If Identity can't answer, the request fails with 503 `Identity.Unavailable`, the same as the authority check that has already run in that request.
  - The lookup isn't called when there are no administrators to name.
- Queries open no command transaction.

## API contract (only for API tasks)
No new route. Both existing routes keep authentication, tenant routing, `no-store` and the error mapping of TASK-DP-025-003.
- **`GET api/v{version}/organizations/{organizationId}/engagements/{engagementId}`:**
  - **Full tier:** the existing `EngagementDetail` fields plus `projects: [{ id, name, status, administrators: [{ userId, displayName }] }]`.
  - **Summary tier:** a **separate** record `EngagementSummary { id, clientDisplayName, engagementName, agreementReference, status, milestones, version }`. It is a different type, not `EngagementDetail` with nulls, so money fields can't leak by being left null.
  - Both shapes carry `tier: "full" | "summary"`, so a client can tell them apart.
- **`GET .../engagements`:**
  - Items become `EngagementListEntry`, polymorphic with discriminator `tier` (`[JsonPolymorphic(TypeDiscriminatorPropertyName = "tier")]` with `[JsonDerivedType]` `"full"` / `"summary"`).
  - `"full"` items carry the existing detail fields. **The list does not include `projects`,** to avoid one directory call per page; the page still costs a single query per child table.
  - `"summary"` items carry the summary fields.
  - Ordering, `status` filter, `limit` and cursor are unchanged; summary-tier engagements are mixed in by the same ordering.
- **Errors:** as TASK-DP-025-003, plus 503 when the user directory can't answer on the detail route.

## Implementation plan
1. **Application:**
   - `ReadAccess` gains nothing; the summary check is data, not authority.
   - Add `EngagementTier`, `EngagementSummary`, `EngagementListEntry` (base plus `Full`/`Summary` derived records), `EngagementProjectView`, `EngagementAdministratorView` and `IUserDirectory`.
   - `IEngagementReadStore`: `ListAsync` returns an `EngagementPage` of `EngagementListEntry`. `GetAsync` returns a result that is either full, with a project/administrator ID list for naming, or a summary. Add `ListProjectsAsync(org, engagementId)` if it reads better.
   - `CanReadAsync` stays full-tier only for history.
2. **Handlers:**
   - `GetEngagementHandler` resolves names through `IUserDirectory` for the full tier only and returns a typed polymorphic `EngagementView` (full or summary, discriminated by `tier`).
   - `ListEngagementsHandler` maps rows to entries.
3. **Infrastructure:**
   - `EngagementReadStore` defines one `Visible` query returning `(engagement, tier)`. The tier is computed as `CanReadAll || CreatedByUserId == UserId ? Full : Summary`, where Summary requires the member-participation `EXISTS`.
   - It loads contacts and link-code data only for full rows, milestones for both, and projects with active administrator IDs for the full detail.
   - `IdentityAuthorityClient.LookupUsersAsync` and `IdentityUserDirectory`, which batches by 100 and maps failures to `ServiceUnavailableException("Identity.Unavailable", …)`.
4. **API:** response types only in `EngagementsController`; check that the JSON contains `tier` and the derived fields.
5. Update `ARCHITECTURE.md`'s Projects read description and the Identity consumers line if they list callers.
