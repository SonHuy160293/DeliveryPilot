# TASK-DP-025-011 — Engagement summary for project participants and projects on the engagement page

## Objective and source contract
Complete the visibility tiers of [FR-DP-025-006](../fr/FR-DP-025-006.md): a money-free summary for member participants of a project under the engagement, and the list of projects (name, status, administrator names) on the full-detail engagement page. Sources: [FR-DP-025-003](../fr/FR-DP-025-003.md), [FR-DP-025-006](../fr/FR-DP-025-006.md); [US-DP-025-006](../us/US-DP-025-006.md) AC-002 and AC-003; [US-DP-025-003](../us/US-DP-025-003.md) AC-004; OQ-025-07, OQ-004-08. All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

**Status: blocked.** This is a provisional plan and must not be implemented until the blockers below are resolved and the task is reviewed with `$dp-task-planner review-task TASK-DP-025-011`.

## Codebase evidence

## Scope and dependencies
**In scope:** the summary tier in the list and detail queries of [TASK-DP-025-003](TASK-DP-025-003.md); the projects section of the full-detail engagement page.

**Out of scope:** project content; guest access to engagements (guests get nothing, OQ-025-07); FEAT-DP-015 sharing.

**Depends on:** [TASK-DP-025-003](TASK-DP-025-003.md), plus two prerequisites:
1. [TASK-DP-004-002](../../FEAT-DP-004-project-initialization/tasks/TASK-DP-004-002.md), which creates `project.Projects`, `ProjectParticipants` and `ProjectParticipantRoles`;
2. the Identity batch user lookup for administrator names, [PRJ-20](../../../architecture/modules/projects/design-decisions.md#prj-20), planned as [TASK-DP-003-024](../../FEAT-DP-003-organization/tasks/TASK-DP-003-024.md).

## Behavior and invariants
- Summary tier: a caller with an active participation of `Kind = Member` in a project whose `EngagementId` is this engagement sees client display name, engagement name, agreement reference, status and milestones only. No contract value, effort, contacts, history or link state.
- Guests never see engagement records, although they share the participant table (ERD read models).
- A caller in both tiers gets full detail. A participant removed from the project loses the summary on the next request.
- Full-detail page: each project under the engagement with name, status and the names of its active Project Administrators; no project content and no way to open the project from this entitlement.
- Tenant filter first, then tier.

## API contract (only for API tasks)
Extends the responses of the routes in [TASK-DP-025-003](TASK-DP-025-003.md); no new route is expected. The summary response is a distinct shape, not the detail shape with nulls, so money fields cannot leak by omission. To be confirmed at review.

## Persistence, events and integrations
Read-only joins from `engagement.Engagements` to `project.Projects` and participants inside the module database. Names come from Identity and are never stored (PRJ-12).

## Executor handoff
Do not start. When unblocked, the executor's module is `DeliveryPilot.Projects`, `Features/Engagements/Queries/`.

## Test matrix
- **Summary:** a member participant sees the summary without money, effort or contacts (US-DP-025-003 AC-004, US-DP-025-006 AC-003).
- **Guest:** a guest of a project under the engagement gets an empty list and 404.
- **Removed participant:** loses the summary.
- **Projects on page:** a read-all holder sees project name, status and administrator names and cannot open the project (US-DP-025-006 AC-002).
- **Cross-tenant:** no project or engagement of another workspace is returned.
