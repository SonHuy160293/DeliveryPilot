# TASK-DP-025-004 — Update engagement details and agreement reference

## Objective and source contract
Let a manage holder correct an Active engagement's client details and agreement fields with optimistic concurrency and attributable history. Sources: [FR-DP-025-002](../fr/FR-DP-025-002.md), [FR-DP-025-010](../fr/FR-DP-025-010.md); [US-DP-025-002](../us/US-DP-025-002.md); OQ-025-08, OQ-025-12. - `ProjectsUnitOfWork` owns the command transaction and commit; no handler or store calls `SaveChangesAsync`. Validators throw `CqrsValidationException` (see `SetEngagementContractValueValidator`).

- No migration is needed: every column already exists in `engagement.Engagements`.

## Behavior and invariants
- The handler first calls `IWorkspaceAuthority.RequireAsync` with `organization.engagements.manage`, uncached. A caller without the code gets 403 before any engagement is loaded, so nothing about the engagement is revealed.
- It then loads the engagement by `(OrganizationId, Id)` with a row lock (`FOR UPDATE`). No row gives 404.
- A Closed engagement gives 409 `Engagement.Closed` and no change (FR-DP-025-007).
- Every accepted change increments `Engagements.Version` and appends exactly one `engagement.EngagementEvents` row in the same transaction, with `ActorUserId`, `ActorOrganizationId`, UTC `OccurredAt`, `Reason`, `Details` (previous and new values) and the resulting `EngagementVersion`.
- A request that changes nothing appends no event and does not change the version.
- The pipeline transaction commits; the handler does not call `SaveChangesAsync`.
- Field rules are those of FR-DP-025-001, applied through `EngagementFields` (trimmed values; country upper-case ISO 3166-1 alpha-2; HTTPS document link).
- Order of checks after the lock, as in the other mutations: `EnsureActive()` (409 `Engagement.Closed`), then `RequireVersion(expectedVersion)` (409 `Engagement.VersionConflict`), then the change.
- **Full replacement (PUT):** the body carries all seven fields. An omitted or null optional field clears it; required fields cannot be cleared. Comparison uses the normalized values, so whitespace-only differences are no-ops; a case-only change to the agreement reference is a change.
- A change to the agreement reference or signed date requires a non-blank reason (domain check, 400); other fields accept an optional reason (≤2000 characters, the limit used by the other mutations).
- One event per request: `engagement.details-changed`, listing only the fields that changed.
- **Duplicate warning (proposal, follows FR-DP-025-001 / OQ-025-11):** when the agreement reference changes, take the same `engagement.reference:v1:…` advisory lock as creation for the new reference, after the row lock, so a concurrent create and update see each other. The result's `duplicateAgreementReference` is true when another Active engagement of the workspace (excluding this one) has the same trimmed, case-insensitive reference. The update still succeeds. Creation takes only the reference lock and never the row lock, so this order cannot deadlock with it.

## API contract (only for API tasks)
- **Route base (proposed, mirrors Identity):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/engagements`. Not exposed through the Gateway until TASK-DP-025-013.
- **Authentication and tenant:** `[Authorize]`. User ID and session ID come from `ICurrentUserProvider` (`CurrentUser.Id`, `CurrentUser.SessionId`). The workspace is the route `organizationId`, confirmed by `IWorkspaceAuthority`; it is never taken from token claims or the body (BR-008).
- **Errors (through `GlobalExceptionHandlingMiddleware`):** 400 `CqrsValidationException`; 401 no valid session; 403 `ForbiddenException` when Identity denies the workspace or the required code is missing; 404 `NotFoundException` for an engagement of another workspace or outside the caller's visibility, with the same response in both cases; 409 `ConflictException`; 503 `ServiceUnavailableException` when Identity cannot answer (fail closed).
- **Method and route (proposed):** `PUT .../engagements/{engagementId:guid}`.
- **Body (`UpdateEngagementRequest`, proposed):** `expectedVersion` (required, positive), `clientDisplayName`, `agreementReference`, `agreementSignedOn` (required), `clientLegalName`, `clientCountryCode`, `engagementName`, `documentUrl` (optional; null clears), `reason` (required when the agreement reference or signed date changes). Unknown members give 400. `[RequestSizeLimit(16384)]`.
- **Success:** 200 with `id`, `status`, `version`, the seven fields, `updatedAt` and `duplicateAgreementReference`. A no-op returns the same shape with the unchanged `version`.
- **Errors:** 400 for invalid fields or a missing reason on an agreement change; 409 `Engagement.Closed` or `Engagement.VersionConflict`.

## Implementation plan
1. **Domain:** `Engagement.UpdateDetails(...)` normalizes through `EngagementFields`, calls `EnsureActive()`, requires a reason when the reference or signed date changes, returns the changed fields (empty on no-op) and advances the version only when something changed.
2. **Application:** `Features/Engagements/Commands/UpdateEngagementDetails/` with command, validator (ids, positive `expectedVersion`, field rules, reason length) and handler following `SetEngagementContractValueHandler`; a result record for the response. Add `LockReferenceAsync` and `HasOtherActiveReferenceAsync(organizationId, reference, excludeEngagementId)` to `IEngagementMutationStore`.
3. **Infrastructure:** implement both in `EngagementMutationStore` with the same lock key and `lower()` comparison as `EngagementCreationStore`; share the key format rather than copying the string.
4. **API:** `UpdateEngagementRequest` in `Contracts/Engagements/` and a `PUT {engagementId:guid}` action on `EngagementsController`.
5. **Tests:** in `EngagementMutationHttpTests`.

## Test matrix
- **Positive:** changing the agreement reference with a reason updates the value, increments the version and appends an event with previous and new values, actor, reason and UTC time.
- **Reason:** agreement reference or signed date changed without a reason gives 400; changing only the engagement name without a reason succeeds.
- **Concurrency:** two requests from the same version; one succeeds and the other gets 409.
- **No-op:** identical values, or values differing only in surrounding whitespace, give 200 with the same version and no new event.
- **Clearing:** omitting `clientLegalName` clears it and the event lists previous and new (null) values; omitting a required field gives 400.
- **Field rules:** invalid country, non-HTTPS document link, over-long fields and unknown body members give 400 and no change.
- **Duplicate warning:** changing the reference to one held by another Active engagement succeeds with `duplicateAgreementReference: true`; to one held only by a Closed engagement, or unchanged, gives `false`.
- **History:** the change appears in the history API with only the changed fields.
- **Authorization:** the engagement creator without the manage code gets 403; Identity unavailable gives 503; nothing changes.
- **Cross-tenant:** an engagement ID of another workspace gives 404.
- **Closed:** every route of this task gives 409 on a Closed engagement.
