# TASK-DP-025-007 — Manage client contacts and the client Product Owner designation

## Objective and source contract
Let a manage holder record client contacts on an engagement, with at most one designated client Product Owner, granting no access. Sources: [FR-DP-025-005](../fr/FR-DP-025-005.md), [FR-DP-025-010](../fr/FR-DP-025-010.md); [US-DP-025-005](../us/US-DP-025-005.md); OQ-025-06; PRJ-09. All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

## Codebase evidence
Reviewed 2026-11-11 against the current checkout, including the uncommitted engagement work. TASK-DP-025-002 is done. `EngagementMutationService` authorizes `organization.engagements.manage`, locks the tenant-scoped engagement row and rechecks authority; `ProjectsUnitOfWork` owns command commit. The contact entity and its tenant-scoped table already exist, including the partial unique index for a live client PO. Full-detail reads already return non-removed contacts; the existing milestone commands, API and PostgreSQL HTTP tests supply the established patterns. Replacing a designation must demote the old contact before inserting or promoting the new one while the parent lock and pipeline transaction are held, so the immediate PostgreSQL unique index cannot reject a valid replacement. No migration or cross-module access change is needed. The user requested implementation; linked requirements remain `ready` with `approval_ref: null`.

## Scope and dependencies
**In scope:** add, edit and remove contacts; designate the client PO.

**Out of scope:** any user, membership, guest grant or decision authority; offering the designated PO as default invitee (FEAT-DP-004).

**Depends on:** [TASK-DP-025-002](TASK-DP-025-002.md). It changes the same aggregate and controller as the other engagement mutation tasks, so run them one at a time.

## Behavior and invariants
- The handler first calls `IWorkspaceAuthority.RequireAsync` with `organization.engagements.manage`, uncached. A caller without the code gets 403 before any engagement is loaded, so nothing about the engagement is revealed.
- It then loads the engagement by `(OrganizationId, Id)` with a row lock (`FOR UPDATE`). No row gives 404.
- A Closed engagement gives 409 `Engagement.Closed` and no change (FR-DP-025-007).
- Every accepted change increments `Engagements.Version` and appends exactly one `engagement.EngagementEvents` row in the same transaction, with `ActorUserId`, `ActorOrganizationId`, UTC `OccurredAt`, `Reason`, `Details` (previous and new values) and the resulting `EngagementVersion`.
- A request that changes nothing appends no event and does not change the version.
- The pipeline transaction commits; the handler does not call `SaveChangesAsync`.
- A contact has name (trimmed, 1–200), email (valid, stored trimmed and lower case) and role `ClientProductOwner` | `Sponsor` | `Other`.
- Designating a contact as client PO, at creation or by edit, changes any other non-removed `ClientProductOwner` contact of the engagement to `Other` in the same transaction (PRJ-09). The partial unique index is the final guard.
- A replacement records one combined `contact.designated-client-po` event for the new contact. Its details record both contact IDs and both previous/new role values, so the previous contact's demotion and the new designation remain attributable in one history entry (user-selected clarification, 2026-11-10; FR-DP-025-010).
- Removal sets `RemovedAt`/`RemovedByUserId`; the row stays. Removed contacts are not returned by the detail read.
- Edits and removals use the contact's own `expectedVersion`; the engagement version rule is the one of TASK-DP-025-006.
- Contacts are personal data (NFR-008): contact names and emails are not written to application logs.
- Nothing in Identity or in project access changes.

## API contract (only for API tasks)
- **Route base (proposed, mirrors Identity):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/engagements`. Not exposed through the Gateway until TASK-DP-025-013.
- **Authentication and tenant:** `[Authorize]`. User ID and session ID come from `ICurrentUserProvider` (`CurrentUser.Id`, `CurrentUser.SessionId`). The workspace is the route `organizationId`, confirmed by `IWorkspaceAuthority`; it is never taken from token claims or the body (BR-008).
- **Errors (through `GlobalExceptionHandlingMiddleware`):** 400 `CqrsValidationException`; 401 no valid session; 403 `ForbiddenException` when Identity denies the workspace or the required code is missing; 404 `NotFoundException` for an engagement of another workspace or outside the caller's visibility, with the same response in both cases; 409 `ConflictException`; 503 `ServiceUnavailableException` when Identity cannot answer (fail closed).
- **Routes (proposed):**
  - `POST .../engagements/{engagementId:guid}/contacts`;
  - `PUT .../contacts/{contactId:guid}`;
  - `POST .../contacts/{contactId:guid}/remove`.
- **Bodies:** add: `name`, `email`, `contactRole`. Edit: `expectedVersion`, `name`, `email`, `contactRole`. Remove: `expectedVersion`, `reason` (optional). `POST` add returns 201.
- **Success:** 200 with the updated resource and its new `version`.
- **Errors:** 400 for an invalid email, blank name or unknown role; 404 for a contact not in this engagement or already removed; 409 `Contact.VersionConflict` or a Closed engagement.

## Persistence, events and integrations
Events `contact.added`, `contact.changed`, `contact.designated-client-po`, `contact.removed` with `SubjectType = Contact`. `Details` hold previous and new name, email and role; history is visible only to the full-detail tier.
No outbox message: no consumer exists yet (ADR-001 D-10).

## Test matrix
- **Designate:** a contact added as client PO is shown as the designated PO.
- **Replace:** designating a second contact leaves exactly one `ClientProductOwner`; the first becomes `Other`; history shows both changes.
- **Concurrent designation:** two parallel designations end with exactly one designated PO.
- **Invalid:** `not-an-email` gives 400.
- **Remove:** the removed contact disappears from the detail read and stays in history; removing the designated PO leaves the engagement without one.
- **No access:** no Identity call other than the authority check is made, and no row outside `engagement` is written.
- **Authorization:** the engagement creator without the manage code gets 403; Identity unavailable gives 503; nothing changes.
- **Cross-tenant:** an engagement ID of another workspace gives 404.
- **Closed:** every route of this task gives 409 on a Closed engagement.
