# TASK-DP-025-010 — Confirm and remove a client organization link

## Objective and source contract
Let an Owner or Admin of an existing Identity organization preview and confirm a link code while acting in that organization, list the engagements linked to it, and let either side remove a confirmed link, including on a Closed engagement. The link never grants access. Sources: [FR-DP-025-007](../fr/FR-DP-025-007.md), [FR-DP-025-009](../fr/FR-DP-025-009.md), [FR-DP-025-010](../fr/FR-DP-025-010.md); [US-DP-025-008](../us/US-DP-025-008.md) AC-002…AC-006; OQ-025-10, OQ-025-13; PRJ-10, PRJ-17; ADR-001 D-08, D-09. All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

## Codebase evidence
Reviewed 2026-11-11 against commit `f84a9d5` and the completed TASK-DP-025-009 work in this checkout. `EngagementMutationService` authorizes the vendor, acquires the tenant-scoped engagement row lock, then rechecks authority; the command pipeline commits through `ProjectsUnitOfWork`. The engagement, code, attempt and append-only event tables already exist. Issuance uses exactly 32 uppercase ungrouped Crockford-base32 characters and stores the SHA-256 of that exact string; the code and verifier are absent from subsequent detail and history reads. `WorkspaceAuthority` provides Owner/Admin facts. Existing PostgreSQL-backed HTTP tests exercise row locks, authorization and rollback. Confirmation must recheck the code under the same engagement lock; a separate per-user limiter, on its own connection, must hold its lock from the count until the handler exits and commit failed attempts independently. Holding it until the handler exits is enough: only failures count, and each failure is committed on the limiter's connection before the lock is released, so a success committing later cannot admit an extra guess. The user requested this task as a prerequisite for FR-DP-025-007. No requirement approval status is changed.

## Scope and dependencies
**In scope:** preview, confirm, client-side list, client-side remove, vendor-side remove, failed-attempt counting and limit.

**Out of scope:** any project participation, guest grant or membership change; issuing codes ([TASK-DP-025-009](TASK-DP-025-009.md)).

## Behavior and invariants
- **Client side acts in organization C** (the route `organizationId`). `IWorkspaceAuthority.RequireAsync(user, C, session, null)` must report `IsOwner` or `IsAdmin`; a plain Member, a denied membership or an invalid session gives 403.
- **Rate limit first:** before a code is verified, count the caller's `EngagementLinkAttempts` rows in the window. At or over the limit gives 429 without verifying. Limit and window are configuration (proposed defaults: 5 failures per 15 minutes per user).
- Serialize the count, verification and failed-attempt recording per user across API instances (e.g. a PostgreSQL session advisory lock on a dedicated connection, released in `finally`). Keep the lock until success or the independent failed-attempt commit; a count-then-insert race must not admit extra guesses. The limiter's connection/transaction must not join the pipeline transaction.
- **Lookup:** by `SHA-256(code)` on the globally unique `CodeVerifier`, without an `OrganizationId` filter: this is the documented exception, because the client does not know the vendor workspace.
- **A code is valid** when its status is `Outstanding`, it is not expired, its engagement is Active and has no link, and C differs from the engagement's `OrganizationId`. Every other case, including an unknown code, gives the same generic failure (`EngagementLink.InvalidCode`, 404 proposed) and records one failed attempt.
- **The failed-attempt row must commit although the request fails** (PRJ-17). Write it outside the rolled-back command transaction, for example in its own short transaction, and prove it with a test.
- **Preview** returns only the engagement name and client display name and changes nothing.
- **Confirm** locks the engagement row, sets `ClientOrganizationId = C`, `ClientLinkedAt`, `ClientLinkedByUserId`, marks the code `Consumed` with the consumer columns, increments the engagement version and appends `link.confirmed` with `ActorOrganizationId = C`.
- After acquiring that lock, reload the code and recheck its status, expiry, engagement state and existing link before changing anything. Issue, close and confirm use the same engagement lock; an earlier lookup or preview is never sufficient authorization to consume a code. Removal also locks the engagement and rechecks the current linked organization before clearing it.
- **Client list** returns engagements where `ClientOrganizationId = C`, with engagement ID, engagement name and client display name only.
- **Remove** clears the three client-link columns and appends `link.removed`. Allowed for an Owner/Admin of C (client route) and for a vendor manage holder (vendor route), and allowed while the engagement is Closed (OQ-025-13). It is the only mutation that skips the Closed guard.
- Confirming or removing changes no project participation, guest grant or membership.
- Codes and verifiers never appear in logs, events or responses.

## API contract (only for API tasks)
- **Route base (proposed, mirrors Identity):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/engagements`. Not exposed through the Gateway until TASK-DP-025-013.
- **Authentication and tenant:** `[Authorize]`. User ID and session ID come from `ICurrentUserProvider` (`CurrentUser.Id`, `CurrentUser.SessionId`). The workspace is the route `organizationId`, confirmed by `IWorkspaceAuthority`; it is never taken from token claims or the body (BR-008).
- **Errors (through `GlobalExceptionHandlingMiddleware`):** 400 `CqrsValidationException`; 401 no valid session; 403 `ForbiddenException` when Identity denies the workspace or the required code is missing; 404 `NotFoundException` for an engagement of another workspace or outside the caller's visibility, with the same response in both cases; 409 `ConflictException`; 503 `ServiceUnavailableException` when Identity cannot answer (fail closed).
- **Client-side routes (proposed), where `organizationId` is C:**
  - `POST api/v{version:apiVersion}/organizations/{organizationId:guid}/engagement-links/preview` with body `code`;
  - `POST .../engagement-links/confirm` with body `code`;
  - `GET .../engagement-links`;
  - `POST .../engagement-links/{engagementId:guid}/remove` with optional `reason`.
- **Vendor-side route (proposed):** `POST .../organizations/{organizationId:guid}/engagements/{engagementId:guid}/client-link/remove` with `expectedVersion` and optional `reason`.
- **Success:** 200. Preview and list return only engagement name and client display name (plus the engagement ID in the list).
- **Errors:** 403 when the caller is not Owner/Admin of C, or lacks the manage code on the vendor route; 404 generic failure for any unusable code; 404 on remove when the engagement is not linked to C; 409 on the vendor route for a stale version or no link; 429 when the attempt limit is reached; 503 when Identity is unavailable.

## Persistence, events and integrations
- `EngagementLinkAttempts`: one row per failed preview or confirm, with `UserId`, `ActingOrganizationId`, `AttemptedAt`. No code, verifier or engagement reference.
- Events `link.confirmed` and `link.removed`, `SubjectType = Engagement`; `Details`: `{ clientOrganizationId }` and, for confirmation, `linkCodeId`.
- Deleting attempt rows older than the window is optional here; if added, it runs in the Projects worker, not in the request path.

## Implementation plan
1. Domain: `ConfirmClientLink` and `RemoveClientLink` on `Engagement`; consume on `EngagementLinkCode`.
2. Application: commands `PreviewEngagementLink`, `ConfirmEngagementLink`, `RemoveEngagementLinkAsClient`, `RemoveEngagementClientLink`; query `ListLinkedEngagements`; an attempt-limiter abstraction.
3. Infrastructure: verifier lookup, linked-engagement read on the `(ClientOrganizationId)` index, attempt store with its own transaction.
4. API: `EngagementLinksController` for the client routes, one action on `EngagementsController` for the vendor route, 429 mapping.

## Test matrix
- **Confirm:** an Owner of C confirms; the vendor detail read shows C linked; the code is `Consumed`; the event carries `ActorOrganizationId = C`. An Admin of C also succeeds.
- **Member:** a plain Member of C gets 403 on preview and confirm.
- **Unusable codes:** unknown, expired (8 days old), consumed, invalidated, Closed engagement, already linked engagement and C equal to the vendor workspace all give the identical generic failure and one attempt row each.
- **Rate limit:** after the configured number of failures the next attempt gives 429 without a lookup; attempts of another user are not counted; attempt rows survive the failed request.
- **Preview:** returns only the two display fields and changes nothing.
- **Client list:** returns only engagements linked to C, with no vendor fields.
- **Remove:** by an Admin of C and by a vendor manage holder; the link is gone, history remains; both also work on a Closed engagement, which stays Closed.
- **No access:** after confirmation no member of C can call any vendor engagement route for that workspace.
- **Single use:** two parallel confirmations with one code link once; the other gets the generic failure.
- **Concurrent limit and lifecycle:** parallel guesses by the same user across instances cannot exceed the configured allowance; confirmation racing with rotation or close rechecks the current code and engagement under the lock; removal cannot clear a link belonging to another client organization.
- **Secrecy:** events and captured logs contain neither the code nor the verifier.

## Implementation review — 2026-11-12

Preview and confirmation are implemented with one shared flow, Owner/Admin authorization before lookup and after blocking locks, code reload under the vendor engagement lock, and a single attributed confirmation event. Each user has a PostgreSQL session advisory lock on an independent connection; failures commit there before release even if the request disconnects after an invalid verdict. Options default to 5 failures per 15 minutes. The API maps the limit to 429 with Retry-After and no-store. Existing removal/list behavior is retained.
