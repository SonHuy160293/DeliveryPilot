# TASK-DP-025-012 — Projects module deployment wiring

## Objective and source contract
Make the Projects API, worker and migration runner deployable next to Identity and Notification, with their own database and roles, so that engagement endpoints can later be published and checked end to end. This is the pending part of [ADR-001](../../../architecture/adr-001-delivery-module-placement.md) §5 "Deployment impact" (Projects column) and §6 item 3, and gate G5 of the task-readiness workflow. Linked requirement: [FR-DP-025-001](../fr/FR-DP-025-001.md) (first behavior that needs a running Projects API). No user story is invented for this technical task.

## Scope and dependencies
**In scope:** Docker stages; `deploy/compose/projects/compose.yaml` and `compose.local.yaml` (migration job, API, worker); database `DeliveryPilotProjects` with roles `projects_migrator`, `projects_api`, `projects_worker`; grants; broker bootstrap for the Projects outbox; secrets staging; env files; `projects` in the CLI scripts; deployment tests; outbox alerts; documentation.

The user-approved joint plan permits the minimal Projects API secret-file configuration loader and its host tests. The current API validates JWT, outbound Identity and inbound integration keys at startup, but lacks Identity's existing key-per-file loader. Stage Identity's canonical JWT key and outbound integration key, plus a separate Projects inbound integration key, into API-only configuration files. Load them before service registration; worker/migration hosts receive none of those keys.

**Out of scope:** the Gateway `projects` cluster and routes ([TASK-DP-025-013](TASK-DP-025-013.md)); application behavior beyond the secret configuration hook; a third bearer-validating host (ADR-001 D-02 gate).

**Depends on:** nothing. It can run in parallel with the feature tasks.

## Behavior and invariants
- The API role has no DDL rights; only `projects_migrator` owns schema objects. Migrations run in the migration job, never at API startup.
- The API role gets `SELECT`/`INSERT` only on append-only event tables when they exist (`engagement.EngagementEvents`): no `UPDATE` or `DELETE` (ERD). Write the grant so it applies after the engagement migration of [TASK-DP-025-001](TASK-DP-025-001.md) lands, without failing before it.
- The shared HS256 JWT key is staged for the Projects **API only**, not for the worker or migration runner (ADR-001 D-02). The Identity integration key is staged for the API.
- Secrets are files, never process arguments, logs or image layers, following the existing `stage-secrets.sh` rules.
- The Projects API is reachable only on the internal network; it gets no public port beyond the local development convention used by the other modules.
- Health: `/health/live` and `/health/ready` drive container health checks.
- Accepted defaults: local API/PostgreSQL ports 19093/25433, verification ports 29093/35433, local images `deliverypilot-projects-{api,worker,migration}:local`. Both CLIs support Projects and include it in `all`; local host mode mirrors Docker configuration. Existing env/secret files are preserved. Projects alerts use existing outbox gauges scoped by `service_name`, with their own loaded rule file.

## Persistence, events and integrations
Database bootstrap and grants only; no schema change. Broker bootstrap adds what the Projects outbox relay needs, mirroring the Identity entries. Observability: Projects outbox metrics and alerts follow the existing delivery alert conventions without changing `deploy/delivery/alerts.yaml`'s email scope.
