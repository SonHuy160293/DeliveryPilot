# US-DP-003-006 — Manage workspace roles and assignments

## Story

As an **authorized organization role manager**, I want to **maintain custom roles and ordinary assignments within my delegation ceiling**, so that I can distribute responsibility safely.

## Context and boundaries

AUTHZ-01–06 and DATA-03 are selected. Multiple roles combine allowed permissions only within their organization; protected restrictions still apply. Owner/platform workflows remain separate.

**State:** Jointly reviewed for requirements completeness, not client-approved or executed. Scenarios apply selected built-in defaults, protected-target rules and explicit delegated grants. Sources: [Workflow discovery](../../../deliverypilot-workflow-discovery.md) §2.2/§4; [Identity decisions](../../../architecture/modules/identity/design-decisions.md).

## Acceptance criteria

### AC-001 — Delegated manager

**Given** a non-Admin has explicit organization role-management authority and holds the proposed catalog-delegable permissions.

**When** they create a custom role with only those permissions and assign it to an eligible same-workspace member.

**Then** the definition/assignment is attributable and grants only those permitted organization powers.

### AC-002 — Built-ins protected

**Given** a customer actor attempts to edit Owner, Admin or Member definitions.

**When** the edit is submitted.

**Then** the built-in definition remains unchanged.

### AC-003 — Self-escalation blocked

**Given** a role editor attempts to add a permission they do not hold to a custom role assigned to them.

**When** the change is submitted.

**Then** the change is rejected and no extra authority results.

### AC-004 — Combined roles

**Given** a member holds two valid same-workspace roles with overlapping permitted powers.

**When** their effective permissions are evaluated.

**Then** allowed powers combine once within that workspace and mandatory restrictions still apply.

### AC-005 — Foreign or protected role

**Given** an actor attempts to assign a foreign-workspace role, protected Owner responsibility through the ordinary path, or a platform power.

**When** the assignment is requested.

**Then** the ordinary assignment produces no such grant.

### AC-006 — Regrant history

**Given** a permitted ordinary assignment was previously revoked and current authority permits a new grant.

**When** the role is regranted.

**Then** prior grant/revocation facts remain distinguishable and only the fresh grant supplies current authority.

### AC-007 — No demote-then-remove bypass

**Given** an Admin or delegated role manager is not an Owner and the target has Admin responsibility.

**When** they try to revoke/demote the target’s Admin role.

**Then** the Admin role remains; only an Owner may perform that reduction, even if the actor holds ordinary role-management powers.

### AC-008 — Role input boundaries

**Given** custom-role names are whitespace-only, over 160 characters, case variants of an existing name, or reserved built-in names; a separate description exceeds 1,000 characters.

**When** a manager submits creation/edit.

**Then** invalid inputs cause no change; a permitted trimmed unique name with an optional description within 1,000 characters is eligible.

### AC-009 — Retirement preconditions

**Given** an authorized role manager supplies a valid required retirement reason and the custom role has either a current assignment or a pending invitation offer.

**When** retirement is requested.

**Then** retirement is blocked until both references are cleared; subsequent permitted retirement preserves history and prevents new use.

### AC-010 — Stale edit rejection

**Given** another role/assignment change has committed since the operator read the state.

**When** the operator submits an edit against the stale state.

**Then** the edit is rejected for refresh/review without silently merging or overwriting the newer permission intent.

### AC-011 — Repeated ordinary role operation

**Given** a currently authorized actor repeats an unchanged grant or revocation already reflected in current state.

**When** the repeat is evaluated.

**Then** a current authorized no-change outcome returns without another grant period or fabricated successful state-change event.

### AC-012 — Built-in upgrades are explicit

**Given** a deployment contains a newer built-in permission template without a separately reviewed upgrade.

**When** existing workspace role definitions are evaluated.

**Then** their permission set is not silently changed; customer editing remains prohibited.
