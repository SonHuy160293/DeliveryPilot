## Behavior and invariants

- Registered active authenticated user may create without an existing membership. Accept only name, trim to nonblank 1–160; duplicates across distinct workspaces allowed, no slug.
- Use Idempotency-Key for one same-user creation intent. Canonical request fingerprint uses the trimmed name with ordinal case-sensitive semantics. Matching retries within 24 hours return the same authorized outcome; changed content conflicts. Known expired attempt rejects with explicit new-key/new-intent guidance, never another workspace.
- Serialize same user/attempt with a transaction-scoped parameterized advisory lock before receipt lookup. Successful first intent stores a receipt only in the same commit as workspace, three built-in definitions/permissions, membership, initial Owner and audit. Creation is the explicit initial-Owner exception to requiring an existing Owner.
- On replay require active account/session, active workspace, matching active membership, and current organization.audit.read before disclosing any snapshot field; otherwise generic 403. Check expiry then fingerprint only after authorization. A receipt does not restore membership or authority.
- New attempts acquire attempt advisory lock, then User row and session row FOR UPDATE, and check current eligibility while locked. For existing receipts acquire attempt lock, then existing workspace guard (workspace, ordered Users, memberships), then session row FOR UPDATE; recheck account, session and audit authority with fresh reads. Hold locks through pipeline commit or rollback. Do not acquire an existing workspace lock after the new-attempt User lock.

## API contract (only for API tasks)

**Identity route:** POST /api/v1/organizations; explicit bearer Authorize. Header Idempotency-Key is required nonempty UUID. Closed CreateOrganizationRequest JSON: {"name":"North Team"}. No actor/slug/role fields. Success 201 with ApiResponse data {organizationId,name,status:"active",membershipId,roles:["Owner"],version,membershipVersion,resultKind:"creationSnapshot",snapshotAt}; authorized replay returns the identical snapshot data with 200 and no mutation. These fields describe creation-time facts, never current authority. Use no-store and do not use CreatedAtAction for a nonexistent read route. Gateway publication remains task 014.

400 Validation.Failure for invalid/unknown fields/key; 401 invalid identity; generic 403 Organization.AccessDenied if caller cannot view a known result; 409 Organization.CreationAttemptConflict for changed fingerprint or CreationAttemptExpired for expired attempt; 500/503 safe failure without any created fragment. No response includes an unrelated workspace. Shared envelope/body/correlation conventions apply.

## Unresolved decisions

### Task review — 2026-11-04

TASK-DP-003-002, TASK-DP-003-003 and TASK-DP-003-004 are marked done. The current Identity DbContext contains the core workspace and audit sets; the capability catalog supplies built-in role seeds, and current-state authorization and audit staging are present. Their completion removes the originally recorded dependency blocker, but does not by itself make this task executable.

The planned receipt stores only the workspace ID and request fingerprint, while the API contract requires the original response data on replay. The workspace name/version and the creator's membership version and roles can change after creation, so the specified receipt and mutable current state do not establish how to reproduce that original response. Moreover, current membership alone does not grant access to historical roles: the feature reserves historical role information for authorized audit readers. A review of the replay representation and disclosure check is needed to satisfy both the original-outcome requirement and current authorization without exposing a revoked historical role as current authority. The reviewed task must specify what evidence is retained and how each returned field is authorized, including after role or membership changes.

The creation path also needs an explicit concurrency contract for current account eligibility through commit, consistent with ACCESS-02/U19 and the existing mutation guard's account-row locking. The attempt advisory lock only serializes the same creation intent; it does not itself serialize account-state changes. Specify the account eligibility check, lock order and a race test before implementation.
