# TASK-DP-003-022 — Register the engagement-manage workspace capability code

## Objective and source contract

Add `organization.engagements.manage` to Identity's code-controlled capability catalog as catalog policy version 3. The planned Projects module will check it, through the existing internal authority check ([TASK-DP-003-019](TASK-DP-003-019.md)), before anyone edits an engagement, changes its contract value, effort, milestones or contacts, closes or reopens it, issues a client link code, or removes a client link.

## Behavior and invariants

- `CurrentCatalogPolicyVersion` and `CurrentTemplateVersion` become 3.
- `Version3DelegablePermissionSet` is frozen as the version 2 delegable codes plus `organization.engagements.manage`. `Version3KnownPermissionSet` adds `organization.ownership.manage`. `IsClassifiedGrant` gains a `3` arm, and unknown versions still fail closed.
- Version 1 and 2 rows keep their exact meaning. A version 1 or 2 row that names `organization.engagements.manage` is ignored.
- New organizations seed the code on Owner (all codes) and Admin (delegable codes). Member stays empty.
- Custom roles may receive the code through existing role management, within delegation limits (FR-DP-003-009). Granting it bumps the role's permission-set version, as any permission change does.
- The authority check returns the code in `EffectivePermissions` for holders. Holding it grants no project content access (FR-DP-003-007).
- The upgrade is attributable: one `organization.role.permissions-changed` audit event per upgraded role, with actor kind `system` and reference `catalog-policy-v3-upgrade`.

## Persistence, events and integrations

New data-only migration, `UpgradeBuiltInRolesToCatalogPolicyV3`, following the version 2 migration. It needs no model snapshot change.
- **Targets:** non-retired roles with `Origin = 'system'` and `Code IN ('owner','admin')` that do not yet hold `organization.engagements.manage`.
- **Up:**
  - insert the version-3 row for the code (`ON CONFLICT DO NOTHING`);
  - set `Version` and `PermissionSetVersion` to their previous values + 1 and `TemplateVersion = 3`;
  - write one system audit event per role. Its details use the same schema as the version 2 upgrade, with `addedPermissionCodes = ["organization.engagements.manage"]`.
- **Down (best-effort):**
  - remove the upgraded grants and the upgrade audit events;
  - restore the previous permission-set and template versions;
  - advance `Version` again, so optimistic concurrency stays monotonic;
  - leave custom-role grants made after the upgrade in place, where the version 2 catalog ignores them.

No new events and no integration contract changes: `OrganizationAuthorityCheckResult.EffectivePermissions` already carries any code.

## Test matrix

- **Positive:** a new organization's Owner and Admin hold `organization.engagements.manage` as a version 3 row; Member holds none. The authority check returns the code for Owner and Admin.
- **Versioning:** version 1 and version 2 grants stay effective alongside version 3 grants. A version 1 or 2 row naming the new code is ignored. An unknown version (4) is ignored.
- **Delegation:** a custom role can receive the code through existing role management; a manager lacking it cannot delegate it (FR-DP-003-009).
- **Migration (PostgreSQL):** an existing Owner/Admin gains the code exactly once, with versions bumped and one schema-valid system audit event. Member and custom roles are untouched; retired roles are skipped. Re-running is a no-op. `Down` restores the previous versions, and `Up` applies again.
- **Invitations:** a pending invitation offering an upgraded built-in role is treated as stale and requires reissue (existing permission-set check).
- **Isolation:** holding the code grants no project resource access; the `CanAccessProjectResource` behavior is unchanged.
