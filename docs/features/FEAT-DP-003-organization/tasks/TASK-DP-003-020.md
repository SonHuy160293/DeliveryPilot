# TASK-DP-003-020 — Register workspace delivery entry-point capability codes

## Objective and source contract

Add the workspace-level permission codes that gate delivery entry points in the planned Projects module to Identity's code-controlled capability catalog. Owners/Admins and custom roles can then grant them through the existing role and assignment flows, and other hosts receive them through [TASK-DP-003-019](TASK-DP-003-019.md).

Sources:
- [ADR-001](../../../architecture/adr-001-delivery-module-placement.md) D-03: workspace entry points live in Identity's catalog; everything inside a project lives in Projects.
- [Requirements](../../../requirements.md) "Project creation/access" rule: Owner/Admin or a delegated Create Project permission may create a project.
- [FR-DP-003-008](../fr/FR-DP-003-008.md)/[009](../fr/FR-DP-003-009.md): custom-role management and delegation limits.
- [FR-DP-003-007](../fr/FR-DP-003-007.md): these codes authorize only the workspace-level entry action and never project content.

## Behavior and invariants

- `CurrentCatalogPolicyVersion` and `CurrentTemplateVersion` are now 2.
- `Version2DelegablePermissionSet` is frozen: version 1 delegable codes plus the three entry codes. `Version2KnownPermissionSet` adds `organization.ownership.manage`.
- A grant row is effective only under the classification of the version it was granted with. Version 1 rows keep their exact meaning, a version 1 row naming a version 2 code is ignored, and unknown versions fail closed.
- New organizations seed the codes on Owner (all codes) and Admin (delegable codes). Member stays empty.
- Custom roles may receive the codes through existing role management, within delegation limits.
- Holding a code grants no project access. `CanAccessProjectResource` is unchanged.

## Persistence

Migration `20261109074711_UpgradeBuiltInRolesToCatalogPolicyV2` is data-only; the model snapshot is unchanged. For each non-retired built-in `owner`/`admin` role that has none of the new codes, it:
- inserts version-2 rows for the three codes;
- advances `Version` and `PermissionSetVersion` by one and sets `TemplateVersion = 2`;
- writes one `organization.role.permissions-changed` audit event with actor kind `system` and reference `catalog-policy-v2-upgrade`. The details use the same fields as the application's permission-change audit.

`Down` is best-effort:
- it removes the upgraded grants and the upgrade audit events;
- it restores the previous permission-set and template versions;
- it advances `Version` again, so optimistic concurrency stays monotonic;
- new-code grants made to custom roles after the upgrade are left in place, and the version-1 catalog ignores them.
