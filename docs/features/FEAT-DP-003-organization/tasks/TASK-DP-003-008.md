## Behavior and invariants

- New planned OrganizationInvitationEmailRequestedV1 in Notification.Contracts, distinct event type notification.organization-invitation-email-requested.v1 and template organization-invitation.v1. Bind MessageId, CorrelationId, producer identity, organization/invitation IDs, issuance identity, UTC issue/deadline and encrypted payload in authenticated associated data; deadline seven days after issuance. Keep old EmailDeliveryRequestedV1 validation unchanged.
- API-side Identity stager encrypts recipient/workspace display/role summary/proof using the Notification public key, and stages request plus ledger in the same future invitation command transaction. Raw proof has redacted ToString and is never a query/log/audit field. API does not host the broker relay; Identity Worker publishes/reconciles the new event explicitly.
- The role summary uses the immutable offer-time name from 007: rename and resend keep it; reissue uses the new offer's captured name. Its text does not grant authority.
- Notification uses distinct contract/intake registration, same delivery repository reliability model, keyed consumer dedup and preserved provider/suppression budgets. New invitation template uses configured trusted origin and reserved /join-workspace fragment carrying invitationId/proof; no query token or arbitrary recipient URL. This is a future client handoff, not an existing browser route.
- Before every provider retry/initial dispatch, query Identity for this delivery ID’s eligibility. Deny superseded/current-marker mismatch, terminal/expired offer, invalid scope or unavailable authoritative result. No database access across modules. A request admitted just before later cancellation cannot be recalled from the provider; old proof still cannot redeem. Dispatch is authorized outside the provider call’s transaction; never hold Identity row locks over network/provider I/O.
- New OrganizationInvitationEmailStatusV1 events distinguish queued/retrying/provider-accepted, verified provider outcome, failed/suppressed/expired/obsolete. Include event ID, delivery ID, monotonic per-delivery sequence, UTC time and allowlisted safe code, never recipient/proof. Project only newer sequence for the current issuance; stale/duplicate/old-generation events cannot regress current status. Intake acknowledgement is never Delivered. Reuse the unchanged EmailDeliveryRecordedV1 intake-ack envelope for the new request only after extending the Identity receipt store’s allowed originating message types/recovery scan to include both request types. Status events separately validate fixed Notification producer, UUIDv7 IDs, positive sequence and allowed states/codes; duplicate event ID with conflicting payload is rejected without projection mutation.
- Delivery failure leaves invitation pending with visible status; automatic retry reuses proof without expiry extension. Preserve existing provider idempotency/attempt/circuit-breaker budgets (including first-attempt retry window); do not infer that a seven-day offer guarantees seven days of provider retries. At dispatch revalidate again even for frozen payload.

## API contract (only for API tasks)

**Private service route:** GET /api/v1/integrations/organization-invitation-deliveries/{deliveryMessageId}/eligibility. Dedicated X-Invitation-Dispatch-Key checked constant-time against configured purpose-specific key; do not accept ordinary Users-integration keys or bearer/tenant claims as this service power. New Identity.Contracts decision DTO {allowed:boolean,expiresAt:UTC|null}; no organization names, addresses, member or proof data. Unknown/obsolete IDs return allowed:false without distinguishing existence. 401 bad service key; 503 unavailable facts. Never publish this route through Gateway. Notification client has a two-second timeout, fails closed and reschedules within the existing bounded delivery budget. No public invitation-management route in this task.
