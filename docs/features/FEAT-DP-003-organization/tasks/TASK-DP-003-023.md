# TASK-DP-003-023 — Expose internal batch membership and email-match checks for Projects

## Objective and source contract

Give the Projects module two internal, least-disclosure Identity queries about users **other than the caller**, so that it never reads Identity data or receives more than a yes/no:

1. **Batch membership check** ([PRJ-18](../../../architecture/modules/projects/design-decisions.md#prj-18)): for one organization and 1–100 user IDs, which users are active members.
2. **Email match** ([PRJ-19](../../../architecture/modules/projects/design-decisions.md#prj-19)): does a user's primary email equal a given email under Identity's normalization.

Consumers (all `ready`, `approval_ref: null`):
- [FR-DP-004-006](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-006.md): only current members of the owning workspace become participants.
- [FR-DP-004-008](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-008.md): the acceptor's signed-in email must match; an acceptor who is a member is refused; the inviter's current authority is rechecked at acceptance; a former member is converted (OQ-004-15).
- [FR-DP-004-013](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-013.md): the "no active administrator" flag and Owner recovery depend on administrators' current membership (PRJ-15).
- [FR-DP-003-007](../fr/FR-DP-003-007.md): organization facts never imply project access.

Decisions PRJ-18 and PRJ-19 were user-selected on 2026-11-10. This is a technical task; no User Story is invented.

## Behavior and invariants

- **Membership check:** a user counts as an active member only when the user is active, the membership is active and the organization is active, the same predicate as `IsEligibleActiveMember` plus organization status. An inactive or unknown organization answers `false` for every user, never an error, so callers cannot probe organizations.
- The answer lists each requested user ID once with `isActiveMember`. Duplicates in the request are collapsed. Nothing else is returned: no membership ID, roles, permissions, Owner/Admin flags or reasons.
- **Email match:** `true` only when the user exists, is active and `User.NormalizeEmail(PrimaryEmail) == User.NormalizeEmail(email)`. Unknown, inactive and non-matching all give `false`. The response never contains an email.
- Both read authoritative state uncached, open no command transaction and write no audit event.
- Request and response records override `ToString()` so emails cannot reach logs; the email-match request is not logged by the logging behavior beyond its type name.
- Store failures surface as 503 (fail closed), as for the existing checks.

## API contract (proposed; mirrors the existing authority checks)

Integration key (`X-Integration-Key`); never published through the Gateway.

- **`POST integrations/authority/membership-checks`**
  - Body `OrganizationMembershipCheckRequest { organizationId: Guid (required, non-empty), userIds: Guid[] (1–100, non-empty values) }`.
  - 200 `OrganizationMembershipCheckResult { evaluatedAt, members: [{ userId, isActiveMember }] }`.
- **`POST integrations/authority/email-matches`**
  - Body `UserEmailMatchRequest { userId: Guid (required, non-empty), email: string (required, ≤320) }`.
  - 200 `UserEmailMatchResult { matches: bool, evaluatedAt }`.
- **Errors:** 400 for an empty ID, an empty or over-length list, or a blank or over-length email; 401 without a valid integration key; 503 when Identity's store cannot answer.

## Persistence, events and integrations

Read-only. The membership check loads memberships for `(organizationId, userId IN (...))` in one query joined to users and the organization; add an index only if the existing ones do not cover it. No outbox messages.

## Test matrix

- **Membership:** active member → true; suspended or removed membership, inactive user, unknown user → false; inactive or unknown organization → all false; duplicates collapsed; 100 IDs accepted, 101 rejected.
- **Disclosure:** responses contain only the documented fields; a denied-looking case is indistinguishable from an unknown user.
- **Email match:** exact and case/whitespace-different emails match; another user's email, an inactive user and an unknown user give false; the response and captured logs contain no email.
- **Auth:** missing or wrong integration key gives 401; Gateway does not publish either path.
- **Fail closed:** a store failure gives 503.
