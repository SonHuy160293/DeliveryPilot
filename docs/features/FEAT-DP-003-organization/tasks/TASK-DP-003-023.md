# TASK-DP-003-023 — Expose internal batch membership and email-match checks for Projects

## Objective and source contract

Give the Projects module two internal Identity queries about users **other than the caller**. Each answers yes or no and nothing more, so Projects never reads Identity data directly:

1. **Batch membership check** ([PRJ-18](../../../architecture/modules/projects/design-decisions.md#prj-18)): for one organization and 1–100 user IDs, which users are active members.
2. **Email match** ([PRJ-19](../../../architecture/modules/projects/design-decisions.md#prj-19)): does a user's primary email equal a given email under Identity's normalization.

Consumers (all `ready`, `approval_ref: null`):
- [FR-DP-004-006](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-006.md): only current members of the owning workspace become participants.
- [FR-DP-004-008](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-008.md): the acceptor's signed-in email must match; an acceptor who is a member is refused; the inviter's current authority is rechecked at acceptance; a former member is converted (OQ-004-15).
- [FR-DP-004-013](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-013.md): the "no active administrator" flag and Owner recovery depend on administrators' current membership (PRJ-15).
- [FR-DP-003-007](../fr/FR-DP-003-007.md): organization facts never imply project access.

The user selected decisions PRJ-18 and PRJ-19 on 2026-11-10. This is a technical task, so no User Story is invented. Planned consumers: [TASK-DP-004-007](../../FEAT-DP-004-project-initialization/tasks/TASK-DP-004-007.md) (add participant), [TASK-DP-004-010](../../FEAT-DP-004-project-initialization/tasks/TASK-DP-004-010.md) (guest acceptance: email match, inviter recheck, acceptor-is-member, former-member conversion) and [TASK-DP-004-015](../../FEAT-DP-004-project-initialization/tasks/TASK-DP-004-015.md) (flag and recovery, one batch call per page of projects).

## Behavior and invariants

**Membership check**
- A user is an active member only when the user is active, the membership is active and the organization is active. This is the predicate `EvaluateActorAsync` uses.
- Implement it once, next to `EvaluateActorAsync` in `OrganizationAuthorizationService`, so there are not two definitions of "active member".
- An inactive or unknown organization answers `false` for every user, never an error, so callers cannot probe organizations.
- The response lists each distinct requested user ID once, in first-occurrence request order, with `isActiveMember`. Duplicates in the request are collapsed.
- Nothing else is returned: no membership ID, versions, roles, permissions, Owner/Admin flags or reasons. An unknown user, an inactive user and a removed or suspended membership all look the same: `false`.

**Email match**
- The answer is `true` only when the user exists, `Status == ActiveUserStatus`, and `PrimaryEmail == User.NormalizeEmail(email)`. The comparison runs in SQL because the stored value is already normalized, so the stored email is never loaded or returned. `EmailVerifiedAt` is not required, which matches Identity's own invitations.
- An unknown, inactive or non-matching user gives the same `false`.
- The validator rejects input that `NormalizeEmail` would reject: null, blank, or a trimmed length outside 3–320. The handler therefore never throws `ArgumentException`, and validation messages never echo the email.

**Both queries**
- Each reads authoritative state uncached, in one database round trip, with `AsNoTracking`. Neither opens a command transaction (they are `IQuery`) or writes an audit event.
- Request, query and result records override `ToString()` with their type name. `LoggingBehavior` already logs type names only.
- Store failures and timeouts surface as `ServiceUnavailableException` → 503 (fail closed), never as `false`.

## API contract (proposed; mirrors `users/lookup` and the existing authority checks)

Both endpoints use the integration key (`X-Integration-Key`) and are never published through the Gateway. Each action has `[RequestSizeLimit(16384)]`, `[ResponseCache(NoStore = true, Location = ResponseCacheLocation.None)]` and `return Ok(result.Value)`.

- **`POST api/v1/integrations/authority/membership-checks`**
  - Body: `OrganizationMembershipCheckRequest { organizationId: Guid?, userIds: Guid[]? }`.
    - Unknown members are disallowed.
    - `organizationId` is required and non-empty.
    - `userIds` holds 1–100 entries, none of them `Guid.Empty`. The count is taken before duplicates are removed, as in `users/lookup`.
  - 200: `OrganizationMembershipCheckResult { evaluatedAt: DateTimeOffset, members: [{ userId: Guid, isActiveMember: bool }] }`.
  - Example: `{"evaluatedAt":"2026-11-12T09:00:00+00:00","members":[{"userId":"0190…01","isActiveMember":true},{"userId":"0190…02","isActiveMember":false}]}`.
- **`POST api/v1/integrations/authority/email-matches`**
  - Body: `UserEmailMatchRequest { userId: Guid?, email: string? }`.
    - Unknown members are disallowed.
    - `userId` is required and non-empty.
    - `email` is required, and its trimmed length is 3–320.
  - 200: `UserEmailMatchResult { matches: bool, evaluatedAt: DateTimeOffset }`.
- **Errors:**
  - 400: a missing or empty ID, a missing, empty or over-long list, an empty-GUID entry, a blank or wrongly sized email, or an unknown JSON member;
  - 401: no valid integration key;
  - 413: a body over 16 KiB;
  - 503: Identity's store cannot answer.
- **Namespace:** the records go in `src/Contracts/DeliveryPilot.Identity.Contracts/Authority/` (namespace `DeliveryPilot.Identity.Contracts.Authority`), beside the existing authority records. The item record is `OrganizationMembershipCheckItem(Guid UserId, bool IsActiveMember)`.
- **Consumer handoff:** Projects' `IdentityIntegration` adds `MembershipChecksEndpoint` and `EmailMatchesEndpoint` with exactly these paths.
