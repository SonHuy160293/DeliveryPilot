## Behavior and invariants

- Owner/Admin defaults or separate explicit audit-read grant; member-read alone is insufficient. Every page rechecks active workspace/current authority; revoked readers cannot use historical access.
- Return event ID, actor ID and permitted display name, scope/target IDs, action, UTC time, outcome, aggregate/membership version and ordinal, bounded allowed before/after changes and reason. Never email fields, proof/verifier, credentials or raw request/provider payload.
- Support scoped actor/target/action/time filters. Distinguish past grants from current authority; original attribution remains after removal/rejoin. Keep membership/grant history for workspace lifetime.
- Without membershipId, order ascending by `(OccurredAt, Id)`; with membershipId, filter that exact membership and order ascending by `(MembershipVersion, EventOrdinal, Id)`. The existing membership check constraint guarantees non-null MembershipVersion for matching rows. Include revision/ordinal fields; general ordering is not a claim of causal order.

## API contract (only for API tasks)

**Bearer route:** GET /api/v1/organizations/{organizationId}/audit-events. Query actorUserId?,membershipId?,targetId?,action?,from?,to? plus limit default50/max100 and bounded cursor; reject invalid IDs/windows/actions/cursor with 400, never interpolate arbitrary SQL sort/filter. Timestamps require explicit offsets and normalize to UTC; from is inclusive and to exclusive, with from < to. Filters combine with AND. targetId selects AggregateId; membershipId selects the persisted membership link. Only committed successful events are returned.

Use bounded opaque base64url keyset cursors, maximum 1,024 characters, containing a version, mode, organization ID, normalized filters and the relevant ordering tuple. Validate type, UTC timestamp and nonempty IDs; reject malformed, oversized, wrong-mode, wrong-scope or changed-filter cursors with 400. Use a strict-greater tuple predicate and limit+1; return nextCursor null at the end. Reauthorize every page. The cursor grants no authority and ordering is not a snapshot. The existing organization/time/ID and membership/version/ordinal indexes support the two access paths; inspect generated SQL and plans on PostgreSQL before adding indexes.

200 ApiResponse data {items:[{eventId,actorUserId,actorDisplayName,organizationId,targetType,targetId,action,occurredAt,outcome,aggregateVersion,membershipVersion,eventOrdinal,reason,changes}],nextCursor}; no unrestricted Details serialization. Explicit typed projections cover existing supported event schemas, with bounded arrays/text, unsafe legacy reasons redacted to null and corrupt/unsupported details producing a sanitized 500. Actor names are current permitted display names, including inactive historical actors; system actor user/name fields are null. No protected row existence for denied queries: 401 invalid identity, generic 403 no audit scope, 503 unavailable authoritative facts; scoped empty result is 200 empty items. Success, authentication and error responses use no-store.

### PostgreSQL query-plan evidence

The HTTP query-plan test captures actual EF SQL and typed Npgsql parameters, seeds 6,000 successful events plus one excluded denied event, runs ANALYZE, and replays each continuation query through EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON). Both SQL modes contain organization/success predicates, strict-greater keysets and LIMIT, with no OFFSET or command transaction. A limit of two fetches three rows before the optional actor join. Representative observed plans:

| Mode | Existing index used | Audit rows produced by scan | Execution time |

These local timings are evidence of the tested plans, not performance guarantees. Existing indexes support both access paths; no migration or index was added.
