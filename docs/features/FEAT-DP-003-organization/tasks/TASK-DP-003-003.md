## Scope and dependencies

Add IdentityAuditEvent domain/configuration and Application-owned audit writer plus Infrastructure implementation. No audit-read API, global auth audit rollout, platform administration or durable denied-attempt store.

Prerequisite TASK-DP-003-002 is done; reviewed against resulting source and implemented.

## Behavior and invariants

- Implement the audit envelope/allowlisted event schemas from the dictionary: actor kind and stable identity, scope/target, aggregate and optional membership version/ordinal, UTC times, correlation, outcome and bounded reason. No fabricated system User.
- Preserve before/after membership/grant facts prior to overwriting current fields. Deny unknown payload fields and prohibit email fields, credentials, proof/verifiers and request dumps; reason validation must not echo sensitive input.
- Require nonblank reason up to 1,000 for removal, Admin/Owner reduction, invitation cancellation and custom retirement; optional otherwise. Record only actual committed state changes; no-op replay creates no grant period or false success event.
- Required audit failure rolls back the protected mutation. Denials emit minimal nonsecret telemetry separately; no durable failed-attempt history claim. Retain membership/role history for workspace lifetime; no purge/erasure endpoint.

## Implementation plan

1. Add domain event model and typed allowlist serialization; establish ordered revision/ordinal allocation usable by member and role handlers.
2. Implement writer abstraction in Application and its staging implementation in Infrastructure, registered through existing DI.
3. Add mapping/migration and tests proving failed audit persistence rolls back the same command transaction.
4. Document supported organization event schemas; preserve existing registration/login audit scope and platform exclusions.

## Test matrix

- Multiple child changes at one membership revision receive distinct ordinals; duplicate aggregate/version/ordinal is rejected.
- Failure injection leaves neither business mutation nor a successful audit event.
- Historical grant/removal/rejoin facts survive current-row updates; audit payloads/reasons contain no known forbidden fields or proof.
- Missing/overlong required reasons reject before mutation; denial telemetry is not a successful audit record.
