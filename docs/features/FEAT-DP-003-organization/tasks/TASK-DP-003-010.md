## Behavior and invariants

- Require signed-in active account and current normalized primary-email match plus constant-time purpose-bound generation proof. Preview is narrowly authorized by proof, not by general organization membership; return original offered role meaning and explicit needs-reissue state when current permission/sponsor checks no longer permit acceptance.
- Preview uses each immutable offer-time role name captured by 007, including after rename or resend; a reissue uses its newly captured name. Successful acceptance reports current authorized role data as specified below, not historical names as current authority.
- For Pending acceptance check deadline now, offer permission versions, current inviter/delegation authority, active workspace/target eligibility and current generation. Reissue required for changed permissions or invalid sponsor; no automatic role snapshot update.
- First join creates one durable membership; removed rejoin reuses it/original join time and grants only fresh offered ordinary roles. Changing membership state cannot revive any old grants. Active member uses role management, suspended cannot join.
- Consume proof and stage membership/assignment versions, audit and closed invitation together. Accept/decline/cancel/resend races have one valid winner; no partial consumption. Accepted same subject replay is only a current authorized already-accepted result, never a new grant or access restoration; wrong subject/old superseded proof has no sensitive outcome.
- Proof preview/decline and accepted response do not set EmailVerifiedAt. No project or global session authority is created.

## API contract (only for API tasks)

**Planned bearer routes:** POST /api/v1/organization-invitations/{invitationId}/preview with {proof}; /accept and /decline with {proof,expectedVersion}. JSON proof is base64url for 32 random bytes; no query token, no UserId/email/roleIds from client. ExpectedVersion >=1 for Pending state transitions; a recognized same-subject accepted replay is no-change, not a stale mutation.

All three operations use closed API-local request models, the existing envelope, a 16,384-byte body ceiling, no-store headers on success and failure, and secret-redacted API/Application request ToString output. Proof is taken only from the JSON body; it must not appear in URLs, validation messages, tracing, logs, audit details or response DTOs. Supplied expectedVersion is a positive long; an accepted replay ignores its stale comparison after validating the current subject/proof and current disclosure authority.

Preview 200 -> {invitationId,organizationId,workspaceName,offeredRoles,expiresAt,version,status,canAccept,requiresReissue}; disclose only after recipient proof. Accept 200 -> {outcome:"accepted"|"alreadyAccepted",membershipId,organizationId,roles,membershipVersion}; decline 200 -> {outcome:"declined",status,version}. Roles are current authorized new roles, never historical.

Preview offeredRoles uses the immutable offer shape [{roleId,name,permissionSetVersion}]. Accept/replay roles uses the existing current-role shape [{id,code,name}]. For a proven current pending offer, preview computes canAccept from deadline, workspace, recipient membership, sponsor and role facts; changed permissions or sponsor/delegation authority set requiresReissue=true and canAccept=false. Active/suspended recipient memberships cannot accept. A still-valid recipient may decline a pending offer even when sponsor/role changes require reissue, since declining grants no authority.

400 malformed/unknown body; 401 missing identity; generic 403 Invitation.Unavailable for wrong proof/account/scope without existence detail; matched authorized stale/closed/conflicting state 409; expired Pending cannot transition. Removed/suspended accepted subject receives no restricted replay/access. Safe 500/503 dependency failure leaves no consumed proof or grants.

Disclosure and state ordering: authenticate; internally resolve and load current recipient/offer facts; validate current normalized primary email and the scoped proof before exposing state. Missing offers, missing/invalid proof, wrong accounts and superseded generations share 403 Invitation.Unavailable with no workspace, membership or role fields. Malformed JSON, wrong field types, unknown fields and invalid expectedVersion use 400; the body ceiling uses safe 413. After proof authorization, stale version uses 409 Invitation.OfferChanged, closed/expired preview or pending transitions use 409 Invitation.Closed, and an ineligible pending acceptance uses 409 Invitation.RecipientUnavailable. Pending accept with changed offer/sponsor uses 409 Invitation.OfferChanged and performs no mutation. Inactive workspace scope remains unavailable. Preserve the existing bearer validator's fail-closed behavior.

## Persistence, events and integrations (as applicable)

Reuse 007 ledger/verifier and the workspace lock order. Extend Application-owned invitation persistence/security abstractions with a proposed recipient-specific guarded context; implement it in Identity Infrastructure. This is a separate narrow authorization path, not a relaxation of the active-member manager guard. The pipeline opens the accept/decline command transaction. Resolve the organization from the invitation internally, lock that organization, then re-read the invitation and resolve its immutable sponsor before acquiring account locks. Lock recipient, sponsor and current eligible Owner account rows together in ID order, then the recipient's current session when present, then relevant memberships in ID order. Re-read current membership, offered-role and sponsor/delegation facts under these locks. The organization lock serializes absent-member creation as well as existing-member changes; retain the existing unique organization/user constraint. No caller-supplied workspace or actor field determines scope.

The guarded context supplies authoritative facts; Application coordinates proof/eligibility policy through existing domain rules. An active globally unverified account is eligible. Current sponsor checks reuse the manager offer policy: current issue authority for an original offer or reissue authority for a replacement, plus current role management, held/delegable ceiling, active membership/account and existing owner-continuity constraints. Check offer permission-set versions and saved codes, so permission change-and-revert still requires reissue. Do not require recipient role-management permissions or use the ordinary active-member grant guard to authorize first join.

Preview is a query with no business writes, command transaction, write locks, SaveChanges or proof consumption. Load its multi-query facts in a short read-only repeatable-read snapshot in the Infrastructure read store; use no-tracking reads. Its response is advisory at that read snapshot, and accept repeats every authoritative check under the write guard. A current proof for a pending offer can expose its original role names and needs-reissue state; terminal/expired offers receive the safe post-proof conflict described above.

For first join, create the membership using the existing factory and grant exactly the checked offered roles. For removed rejoin, extend/co-ordinate the domain rejoin operation so any still-unrevoked historical grants are ended before activation; reuse the same membership ID and CreatedAt. Reuse stable assignment rows through Regrant only for newly offered roles, create missing offered rows, and leave other historical roles revoked. Preserve previous grant periods through typed revoke/regrant audit snapshots. Increment membership/assignment versions using the existing domain conventions and stage all membership, grant and invitation-close evidence. The signed-in recipient is the acceptance audit actor; the recorded current sponsor is the fresh grant authorizer. Use server-authored safe attribution/reasons for historical-grant closure, never proof material or client-supplied role decisions.

Accept closes the invitation as accepted with ClosedByUserId set to the recipient; decline closes it as declined without grants. State, proof consumption, versions and audit share the single pipeline commit, with no handler/repository SaveChanges. Closing makes existing delivery dispatch ineligible; no new proof generation, issuance quota entry, broker contract, provider call or cross-module transaction is needed.

Accepted replay first validates the same active account/current email, current proof and ClosedByUserId. It then requires an active workspace and currently eligible membership and returns only current effective role data. It does not rerun a pending acceptance, compare the old expectedVersion, issue grants, change versions, write another success event or restore access. The pending deadline/sponsor/offer checks control new grants; their later changes do not by themselves revoke an already active accepted membership. Removed/suspended or wrong accepted subjects receive generic unavailable feedback. Retain the verifier for this narrowly authorized no-change replay rather than treating a valid replay as a second redemption. Existing closure/membership/assignment fields suffice; no migration or replay table is expected.
