# TASK-DP-003-024 — Expose an internal batch user lookup for display names

## Objective and source contract

Let the Projects module resolve up to 100 user IDs to display data in one call, so engagement and project pages can show names without storing Identity data ([PRJ-20](../../../architecture/modules/projects/design-decisions.md#prj-20), [PRJ-12](../../../architecture/modules/projects/design-decisions.md#prj-12)).

Consumers (all `ready`, `approval_ref: null`): [FR-DP-025-006](../../FEAT-DP-025-client-engagement/fr/FR-DP-025-006.md) and [FR-DP-004-007](../../FEAT-DP-004-project-initialization/fr/FR-DP-004-007.md), administrator names on the engagement page (OQ-004-08); later, actor names in history. Decision PRJ-20 was user-selected on 2026-11-10. This is a technical task; no User Story is invented.

## Codebase evidence

Verified 2026-11-10 against the current checkout:
- `DeliveryPilot.Identity.API/Controllers/UsersController.cs` (`IntegrationApiController`, integration key) exposes `GET integrations/users/{userId}`, which sends `GetUserQuery`.
- `GetUserQueryHandler` loads the user through `IUserRepository.GetByIdAsync` (from `IRepositoryBase`, throws for an unknown ID) and returns `UserIntegrationDto(Id, DisplayName, AvatarUrl, Status)` from `src/Contracts/DeliveryPilot.Identity.Contracts/Users/UserIntegrationDto.cs`. The DTO has no email.
- Tests: `tests/DeliveryPilot.Identity.Tests/Users/UsersHttpTests.cs`.

## Scope and dependencies

**In scope:** one batch query and endpoint returning `UserIntegrationDto` items; tests; `ARCHITECTURE.md` endpoint table.

**Out of scope:** changing `UserIntegrationDto` or the single-user endpoint; the Projects-side client and its use ([TASK-DP-025-011](../../FEAT-DP-025-client-engagement/tasks/TASK-DP-025-011.md) and FEAT-DP-004 read tasks); caching.

**Depends on:** nothing. Unblocks part of TASK-DP-025-011.

## Behavior and invariants

- Input 1–100 user IDs; duplicates collapsed. Output one `UserIntegrationDto` per user found, in any order; unknown IDs are omitted, never an error, so the batch does not fail on one deleted or mistyped ID.
- Users of every status are returned with their `Status`, so callers can show "inactive" for past actors (attribution, BR-007).
- No email or other personal data beyond the existing DTO (NFR-008). Not tenant-scoped: callers are trusted internal hosts and must only ask for IDs they already hold.
- One database query for the whole batch; no command transaction; no audit event.

## API contract (proposed)

Integration key (`X-Integration-Key`); never published through the Gateway.

- **`POST integrations/users/lookup`** with body `UserLookupRequest { userIds: Guid[] (1–100, non-empty values) }`.
- 200 `UserLookupResult { users: UserIntegrationDto[] }`.
- 400 for an empty or over-length list or an empty GUID; 401 without a valid key; 503 when the store cannot answer.

## Persistence, events and integrations

Read-only `WHERE Id IN (...)` on the users table using its primary key. No outbox messages.

## Executor handoff

Module `DeliveryPilot.Identity` (Application query, `UsersController`, Contracts). `implementation_skill: add-cqrs-api-feature` is a routing hint.

## Implementation plan

1. Contracts: `UserLookupRequest` and `UserLookupResult` next to `UserIntegrationDto`.
2. Application: `Features/Users/Queries/LookupUsers/` (query, validator, handler) and a batch read method.
3. API: `POST lookup` on `UsersController`.
4. Tests below; update `ARCHITECTURE.md`.

## Test matrix

- **Positive:** three known IDs return three DTOs with display name, avatar and status.
- **Partial:** two known and one unknown ID return two DTOs and 200.
- **Limits:** 100 IDs accepted; 0 and 101 rejected; duplicates collapsed.
- **Disclosure:** no email in the response.
- **Auth:** missing or wrong key gives 401; the Gateway does not publish the path.
