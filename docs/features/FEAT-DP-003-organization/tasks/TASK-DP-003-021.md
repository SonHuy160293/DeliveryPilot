# TASK-DP-003-021 — Publish Identity access-change events for resource-owning modules

## Objective and source contract

**Disposition — 2026-11-12 (user-confirmed): not needed for MVP; revisit when a cache or outbox consumer appears.** Status remains `blocked` to record this deferral using the supported Task lifecycle. Projects reads Identity authority uncached on every request, so there is no access-change event consumer to serve. The consumer-need question is resolved for MVP; the implementation below is a deferred proposal.

When a consumer exists and this task is replanned, publish versioned, committed access-change events from Identity so resource-owning modules can evict cached workspace authority early and clean up projections:
- membership removed or suspended;
- workspace role granted or revoked, including role permission changes;
- session revoked;
- organization lifecycle changes.

Sources: [FR-DP-003-005](../fr/FR-DP-003-005.md) (ACCESS-02: events support propagation; they are not the sole revocation authority), [FR-DP-003-009](../fr/FR-DP-003-009.md) (role grant/revoke). [ADR-001](../../../architecture/adr-001-delivery-module-placement.md) D-04 (≤30 s read cache evicted early by these events) and D-10 (messages are added when a consumer exists). Identity [minimum external contracts](../../../architecture/modules/identity/design-decisions.md#minimum-external-contracts) "Access-change propagation".

## Scope and dependencies

**Out of scope:** consumers (Projects scaffolding/feature tasks); using events as the only revocation path.

**Depends on:** TASK-DP-003-019, plus an actual cache or outbox consumer and its reviewed design, per ADR-001 D-10. Projects scaffolding chose uncached authority reads and does not unblock this task.

## Behavior and invariants

- Events are staged in the same pipeline transaction as the change (outbox), so only committed changes publish; delivery is at-least-once.
- Payload: event ID, event type, `OrganizationId`, affected `UserId`/`MembershipId`/`SessionId` as applicable, aggregate version, occurred-at (UTC `DateTimeOffset`), correlation ID. No email, names, reasons, credentials or tokens.
- Consumers must deduplicate by event ID and ignore stale versions. Identity makes no ordering guarantee beyond per-aggregate version.
- Event failure never blocks or rolls back the Identity mutation beyond normal outbox semantics.

## Implementation constraints found 2026-11-09

Deferred by the user's plan-mode decision on 2026-11-09, after these source findings:

- **Mandatory publish:** `src/BuildingBlocks/DeliveryPilot.Messaging/MassTransit/MassTransitEventPublisher.cs` publishes with `Mandatory = true`, and the RabbitMQ host uses publisher confirmations. A message sent to an exchange with no bound queue is returned as a failed publish, so the outbox retries it and the "outbox stalled" alert fires. Publishing must not start until a durable consumer queue is bound, for example by declaring the consumer's queue in `deploy/setup/broker-bootstrap.sh` together with the consumer.
- **Outbox retention:** `IdentityOutboxMaintenanceWorker` deletes published rows only when an `EmailDeliveryReceipt` exists, and `IdentityOutboxDispatchStore` reconciles receipts only for email message types. Non-email access-change events need their own retention (delete after publish plus a bounded age) and must stay out of the receipt reconciliation and missing-receipt metric.
- **Registration:** each new message type needs an `IntegrationEventRegistration` and a `bus.Message<T>(...SetEntityName(...))` mapping in `IdentityMessagingExtensions`, under the `deliverypilot.identity.` exchange prefix that the `identity` broker user may already write.

## Unresolved decisions

**Execution remains blocked by the MVP deferral above.** Consumer need is resolved for MVP: uncached per-request authority checks enforce access changes without events. ADR-001 D-04 permits a read cache but does not require one; D-10 cache eviction and projection cleanup are future consumer needs. Publishing without a bound durable consumer queue would stall the outbox under the mandatory-publish constraint above.

**Deferred design question:** one generic `AccessChangedV1` with a change kind, or one message type per change? Decide with the first cache or outbox consumer when this task is revisited. This is not an open MVP decision or a prerequisite for the uncached engagement flow.
