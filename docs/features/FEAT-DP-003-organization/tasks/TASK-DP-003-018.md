# TASK-DP-003-018 — Serialize workspace mutation and session revocation

## Objective and source contract

Implement the user's 2026-11-04 decision that revocation must prevent a session-authenticated Organization mutation from committing afterward. Requirements remain internally ready, without client approval evidence.

## Codebase evidence and scope

The Identity [mutation guard](../../../../src/Modules/DeliveryPilot.Identity/DeliveryPilot.Identity.Infrastructure/Security/OrganizationMutationGuard.cs) locks the organization, users and memberships under the pipeline-owned transaction, but reads the session without a lock. The [session service](../../../../src/Modules/DeliveryPilot.Identity/DeliveryPilot.Identity.Infrastructure/Security/AuthSessionService.cs) locks the session for revocation. New workspace creation locks user then session; replay enters the workspace guard first. The PostgreSQL characterization test demonstrated the race. No schema change or token-policy expansion is required. Explicit actor operations without a session remain distinct.

## Behavior and lock order

For session-authenticated guarded mutations, lock the organization, relevant users in ID order, the actor's session, then memberships in ID order. Validate the session belongs to the actor and is not revoked after acquiring its lock; hold it through command commit or rollback. Creation locks user then session, and replay follows the guarded order; session revocation locks only session and must never wait for a user or workspace lock. If revocation commits first, mutation fails closed; if mutation gets the lock first, revocation waits until its commit or rollback and thus commits afterward. Preserve existing membership checks, account checks, failure behavior, current transaction ownership and cancellation. Do not infer a session for trusted explicit-actor calls.
