# TASK-DP-003-017 — Pin permission classification to the grant policy version

## Objective and source contract

Prevent an existing stored unknown or nondelegable code becoming effective solely because a later catalog recognizes or reclassifies it. AUTHZ-12/U17 requires no silent privilege upgrade. Requirements are ready, not client-approved.

## Codebase evidence

Reviewed 2026-11-04. The original evaluator filtered scoped rows against mutable current sets, and a regression reproduced expansion for Owner, Admin and custom roles. The [evaluator](../../../../src/Modules/DeliveryPilot.Identity/DeliveryPilot.Identity.Domain/Authorization/OrganizationCapabilityCatalog.cs) now also filters against the row's immutable policy-version allowlist; [regression tests](../../../../tests/DeliveryPilot.Identity.Tests/Security/CatalogReclassificationRiskTests.cs) verify reclassification and unknown versions fail closed. The Identity-owned migration pins existing rows to version 1 without changing their permission codes.

## Scope and dependencies

Depends on completed TASK-DP-003-016. Add a grant policy-version marker and immutable versioned allowlists to the shared evaluator and persistence. No external API, upgrade workflow or automatic grant repair; no changes to requirement approval. Existing rows receive the current v1 baseline marker without changing their permission code or expanding authority. Unknown or disallowed v1 codes remain denied; unknown policy versions fail closed. A future policy version must be reviewed explicitly and is not introduced here.

## Behavior and invariants

- At creation every permission row records the current catalog policy version. The immutable v1 allowlists contain exactly the current 11 Owner-known and 10 delegable codes; do not derive v1 from mutable current sets. A grant is effective only if its scoped row is allowed by its recorded version and the current catalog, including current delegability for non-Owner roles. Member remains empty; protected role identity/continuity remain independent.
- Existing v1-known grants retain current behavior; stored unknown codes remain denied if current catalog later adds them. Owner, Admin and custom roles receive no unreviewed new power. Version changes require a separately reviewed authorized grant/upgrade operation, not a deployment-side rewrite.
- Add a positive policy-version column with v1 default for existing rows and new rows through an additive Identity migration; preserve existing role/code data, schema boundaries and downgrade safety. Never touch deployed databases as part of this task.

## Test matrix

- Reclassification regression: mutate an isolated test catalog's current known/delegable classification and prove preexisting v1 Owner/Admin/custom rows cannot gain the synthetic capability. Future/unknown policy versions fail closed; cross-workspace and protected codes stay denied.
- Existing v1 seed, workspace creation, scoped authorization and protected Owner/admin tests pass. Run upgrade/migration tests with existing rows, including a previously unknown code, on isolated PostgreSQL 18 and inspect generated SQL/snapshot; no privilege expansion or data loss.
- Run focused Identity tests, Identity build and docs validation. Record commands, counts, environment, risks and any skipped checks.
