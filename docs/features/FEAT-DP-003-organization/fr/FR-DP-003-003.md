# FR-DP-003-003 — Redeem and expire invitation

## Requirement statement

The system shall accept a workspace invitation only once for its intended authenticated recipient while its proof, deadline, offered permissions and inviter authority remain valid.

**Origin and state:** Jointly reviewed behavioral contract for task planning. [Identity decisions](../../../architecture/modules/identity/design-decisions.md) INV-01/02/04/05/06, AUTHZ-04, MEM-01/02 and U10; [Workflow discovery](../../../deliverypilot-workflow-discovery.md) Q2/Q5. User-selected rules retain their stated scope; BA-derived scenarios elaborate those choices without claiming customer approval or implementation.

## Preconditions and trigger

The intended recipient explicitly accepts using the invitation link while signed in. A first join is eligible; rejoin also requires the separate reviewed membership-state rules.

## Main behavior

Require valid single-use proof and a current normalized primary-email match. Existing global email verification or a separate fresh code is not required; do not silently set global email verification. Check the actual deadline at redemption even if expiry cleanup has not run. Require unchanged offered role permissions and the inviter’s current invitation/delegation authority. If either has changed, do not grant access; require an authorized reissue. **Proposed recipient-review elaboration:** make the intended workspace and offered role combination explicit to the permitted recipient before acceptance, without disclosing it to an unproven recipient. INV-09/U16 requires matching current sign-in and valid proof before preview or decline; selected member/offer field boundaries still govern the displayed information. Successful acceptance consumes the offer and establishes the authorized membership/current grants consistently with attribution. Rejoin follows FR-DP-003-014.

## Validation, business rules and authorization

BR-002/003/006/008; NFR-001/002/003/004/008. Account authentication, invitation proof and workspace authority are separate conditions. A recipient address match alone grants nothing.

## Failure and edge cases

Reject wrong identity, missing/invalid proof, expired, cancelled, replaced or already-consumed proof without new grants. Acceptance racing cancellation/resend/expiry has at most one committed effect. An expired deadline denies even if stored status is pending. MEM-04/U14 blocks active-member invitations in favor of role management, permits newly authorized removed-member rejoin, and blocks suspended joins until explicit restoration. INV-08/U16 permits the same accepted subject to receive an already-accepted outcome with currently permitted information only; no fresh grants or access return after removal/suspension.

## Verification criteria

- Matching authenticated first-time recipient with valid proof, unchanged offer and current sponsor joins with precisely the offered authorized roles.
- An active but globally unverified matching account can satisfy invitation proof without a fresh code or global verification mutation.
- Wrong email, missing link proof and redemption at/after the deadline create no membership/grant.
- Changed offered permissions or lost inviter authority blocks acceptance until authorized reissue.
- Concurrent redemption produces one membership relationship and no repeated grant effect.

Criteria reflect the selected scope and are not executed test results. Explicitly deferred capabilities below are outside this release.
