## Behavior and invariants
1. Issue a signed context for a server-verified user identity only. The login use case supplies the eligible subject; request JSON/headers cannot select subject, tenant, roles or permissions. Use the required claim set in the technical design below, including the session identifier needed for revocation.
2. Issuance and all selected consuming validators must agree on algorithm, key, issuer, audience, time units, claim mapping and clock behavior. Pin accepted signing algorithms to the reviewed choice. Fail startup safely for invalid configuration; never log key material.
3. Read both TTLs from appsettings: access JWT lifetime 10 minutes; refresh lifetime a fixed 7-day maximum from login that rotation does not extend. There is no additional idle timeout or simultaneous-session count limit. Rotate refresh tokens on successful use; reject old-token reuse. Recheck active account status on every protected request and refresh. Apply the configuration validation and zero clock skew in the technical design; the existing 60-minute option and Development validation relaxation are not the user-selected policy.
4. Logout revokes only the current session's refresh token and immediately rejects that session's issued access tokens on subsequent protected requests; other sessions are unaffected, and requests already admitted may finish. Stateless signature/expiry validation alone cannot satisfy this boundary. Use the atomic refresh-versus-logout ordering and validation design below.
5. Any validity dependency outage fails closed. Context-generation failure yields no usable response. A context staged in a transaction must not be delivered before the commit succeeds. Signing and commit ordering must prevent a failed request from exposing usable credentials.
6. Login grants no organization, project, client-sharing or approval authority. Issued claims reflect only reviewed server-owned identity data. Use a test-only protected endpoint to verify 401/403 and no mutation; do not invent production business endpoints for tests.
7. Contexts, signing keys and reusable proofs stay out of logs, exception details, diagnostic ToString and durable security evidence. Return the access token only through the explicitly reviewed successful login contract; it is never included in error or log payloads.

### Concrete technical design for task review

This task design is derived from the confirmed policy and current Identity host; it does not claim an accepted architecture decision or an implemented endpoint. The executor must verify it against current code and report any mismatch before implementing.

- Use an Identity-owned PostgreSQL session row with a random session ID, user ID, UTC creation and fixed refresh deadline, current refresh verifier, and nullable UTC revocation instant. Index the session identifier and user ID; the user reference stays within Identity. Generate at least 256 random bits of refresh secret with a cryptographic RNG and store its SHA-256 verifier, never the raw secret. Encode an opaque refresh credential containing the session identifier and secret; treat the entire credential as secret. A forward migration must preserve existing Identity data. The executable creates session state as part of the command transaction and returns proof only after commit.
- Validate JWT signature, issuer, audience, lifetime and nonempty user/session GUID identifiers in every environment. Use `sub`, `sid`, `iss`, `aud`, `iat`, `exp` and a unique `jti`; bind `sub` and `sid` to the same persisted session. Reuse the current symmetric key configuration with an explicitly pinned HS256 algorithm and zero clock skew; keep signing material in the existing secret mechanism. Read both positive TTL values from appsettings; provide 10-minute access and seven-day refresh values there, with no runtime hardcoded lifetime fallback. The Identity API currently has no appsettings.json; adding the required non-secret settings file is a proposed addition. Validate missing or invalid values at startup.
- Persist the fixed refresh deadline when the session is created. A configuration change affects newly created sessions or newly issued access tokens; it does not retroactively extend an existing session deadline. Refresh expiry does not by itself invalidate an otherwise valid access token: access expiry, session revocation and account status independently control protected access.
- Serialize refresh and logout against the same session row using a transaction-scoped row lock or an equivalent conditional atomic update. After locking, recheck current verifier, unrevoked state, fixed refresh deadline and active user status; rotate the verifier in the same transaction. At most one concurrent use of a refresh token succeeds. The user confirmed that reuse of an old rotated token is rejected without revoking the current valid session.
- Logout revocation commits against that same session row. If refresh commits first, subsequent logout revokes the resulting session; if logout commits first, refresh fails. A refresh response delivered after logout may contain proof that is already invalid, but cannot restore the session. Failed/uncertain commits never produce a confirmed success. Preserve pipeline-owned transaction boundaries and propagate cancellation.
- After cryptographic JWT validation, check current session revocation and active user status against Identity-owned authoritative data on every protected request. The check is uncached to meet immediate invalidation; dependency failures reject access. Its successful check is the admission boundary: a request admitted before logout or suspension may finish. Identity API is the only current configured JWT consumer; future hosts must obtain reviewed access to Identity-owned validation through contracts, never by referencing Identity's DbContext.
- Follow the user-confirmed policy of no additional idle timeout or concurrent-session count limit; the fixed refresh deadline and access expiry apply. Support separate concurrent sessions, with logout affecting only the current session. Session lookup is fail-closed when a row is missing. No background cleanup is introduced by this task; any later cleanup must account for still-valid access tokens and preserve this fail-closed behavior. Replacing the signing key without a compatible key rollout invalidates existing JWTs; automated key rotation is outside this deliverable.
