## Behavior and invariants
1. Validate the closed registration request before starting the command transaction. Email/DisplayName are trimmed; Password is opaque and not trimmed. Canonicalization must match TASK-DP-002-001 and its PostgreSQL uniqueness checks.
2. Through ISender, execute the registration command in the existing pipeline. Under its transaction, check/lock the canonical email. An existing email throws the typed Registration.EmailExists conflict before creating or changing records.
3. For a new identity, create the User and derive a salted, versioned password verifier through an Application-owned hashing abstraction implemented in Infrastructure. Stage User plus credential using TASK-DP-002-001 and propagate cancellation. The pipeline commits before the controller returns 201.
4. Confirmed phase state: explicitly pass active to User.Create; EmailVerifiedAt and LastLoginAt null; retain current en/UTC defaults for Locale/TimeZone. These are server choices, not body fields. The generic factory retains a pending default. Do not infer that a null email-verification time is verified.
5. No access/refresh token, session, verification message, organization, role or approver grant is created. Existing Users integration authentication stays intact; callers cannot set authority through JSON fields or tenant headers.
6. Normal duplicates and commit-time collisions return the same reviewed 409/message. Lost-success retries may receive 409; do not return another person's userId or reset that account. No separate Idempotency-Key protocol is introduced.
7. Command/request diagnostics, validation messages, provider exceptions and HTTP logs must not contain Password or reusable proof. Make secret-bearing ToString output safe; use the existing request-type-only pipeline logging. No new durable audit/abuse subsystem is introduced.

## API contract (proposed addition, not currently implemented)
- **Identity:** POST /api/v1/auth/register, implemented by a proposed AuthController deriving PublicApiController and an HttpPost("register") action.
- **Gateway:** POST /identity/api/v1/auth/register, exact allowlist route to the existing Identity cluster; remove /identity when forwarding. Existing Notification route is retained.
- **Authorization:** Anonymous registration under the confirmed self-service scope; no JWT or integration API key required. A supplied user/role/TenantId cannot control created identity, status or grants. Do not weaken existing protected endpoints.
- **Headers:** Content-Type: application/json; existing optional X-Correlation-Id behavior. No tenant/path/query/Idempotency-Key input and no credential headers required. Preserve configured production HTTPS and trusted forwarding.
- **Transport:** Proposed API-local Contracts/Auth/RegisterUserRequest.cs. JSON uses the existing camel-case convention. Reject unknown fields, especially status, role, tenantId, emailVerifiedAt and userId; do not mass-assign the domain model.

| JSON field | Contract for this phase |
|---|---|
| displayName | Required string; trim; 1–160 characters, consistent with current database bound. |
| email | Required string; trim; syntactically valid email, 3–320 characters; canonical case-insensitive matching with TASK-DP-002-001. |
| password | Required nonempty/non-whitespace string; never trim, echo or log. No extra complexity/expiry policy is introduced in this phase. Overall transport size remains bounded. |

Proposed shared transport bound: 16,384 bytes with a 30-second Gateway timeout, using values already exercised by the Gateway's synthetic test route and satisfying GatewayConfigProvider. Apply matching Identity request-size protection. These are transport limits, not the deferred registration rate/lockout policy. Preserve configured CORS allowlists rather than introducing wildcard origins or catchall routes.

**Success:** 201 Created with proposed local RegisterUserResponse(UserId), wrapped by the existing ApiResponse envelope. Do not use CreatedAtAction or publish a Location pointing to the private Users integration lookup; there is no public GET registration resource.

~~~json
{"displayName":"Alice","email":"alice@example.test","password":"example password supplied privately"}
~~~

~~~json
{"success":true,"data":{"userId":"019a0000-0000-7000-8000-000000000001"},"error":null}
~~~

| Outcome | Status / semantics |
|---|---|
| Missing/invalid fields, malformed JSON or unrecognized fields | 400; existing validation/model-binding envelope; no registration committed. |
| Existing equivalent email, including a concurrent winner | Proposed 409; code Registration.EmailExists; message exactly "This email is exist"; no account update. |
| Oversized request | 413 using current host/Gateway error conventions; no mutation. |
| Unsupported media type | 415 using existing API transport behavior. |
| Unexpected dependency/persistence failure | Safe existing 500 envelope; no success or raw provider/password details. Use existing typed 503 behavior only for a separately justified known unavailable condition, not as a blanket new mapping. |

~~~json
{"success":false,"data":null,"error":{"code":"Registration.EmailExists","message":"This email is exist","errors":null,"traceId":"request-correlation-id"}}
~~~

No 202 response, implicit automatic login or 429/Retry-After policy is added in this phase. A failed Result must be handled explicitly; reading result.Value on failure is not a valid error strategy. Let supported validation/domain exceptions reach the current middleware.
