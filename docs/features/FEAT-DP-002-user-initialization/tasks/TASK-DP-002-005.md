# TASK-DP-002-005 — Deliver session refresh and logout through Identity API and Gateway

## Objective and source contract
Expose the already implemented session rotation and revocation as two public HTTP journeys:
- **Refresh:** exchange the `dp_refresh_token` cookie for a new access token and a rotated cookie (US-DP-002-002, FR-DP-002-005).
- **Logout:** end the current session (US-DP-002-003, FR-DP-002-006).

## Behavior and invariants
1. **Refresh** reads only the `dp_refresh_token` cookie; no body token is accepted.
   - On success it rotates the session, sets the new cookie with the same attributes and the unchanged fixed deadline, and returns a new access token.
   - A missing, malformed, unknown, rotated-away, revoked or expired token, or an inactive user, returns 401 with one generic code and clears the cookie.
   - A rejected old token never revokes the current session (D-004).
2. **Logout** is anonymous-capable and idempotent. It resolves the session to end, in this order:
   - a. If a valid bearer access token is present, revoke the session from its `sub` and `sid` claims.
   - b. Otherwise, if the refresh cookie parses and its verifier matches the session's current verifier, revoke that session for the owning user.
   - c. Otherwise, do nothing.

   In every case return **204 No Content**, clear the refresh cookie and send `Cache-Control: no-store`. Never reveal whether a session existed.
3. **Logout wins (D-006).** Refresh and revoke serialize on the session row.
   - If logout commits first, a later refresh fails with 401.
   - If refresh commits first, the client still holds its access token for the same `sid`. Logout revokes the session row, which ends the newly rotated refresh token and every access token of that session.
   - Clients should therefore send their bearer token with logout. The cookie path covers expired access tokens.
4. **No cross-user effect.** Logout uses only the caller's own token claims or a cookie whose verifier matches. Request bodies, queries and headers cannot name a session or user.
5. **Unexpected failures.** Persistence or transaction failure returns the existing safe 5xx envelope. Logout never returns 204 unless the revocation committed or there was nothing to revoke. The pipeline throws on commit failure, so the controller must emit the response only after `SendAsync` returns.
6. **Privacy.** Tokens never appear in logs, response bodies (refresh returns only the access token), exception messages or `ToString` output. Commands override `ToString`.

## API contract (proposed)
| | Refresh | Logout |
|---|---|---|
| Identity route | `POST /api/v1/auth/refresh` | `POST /api/v1/auth/logout` |
| Gateway route | `POST /identity/api/v1/auth/refresh` | `POST /identity/api/v1/auth/logout` |
| Auth | Anonymous; refresh cookie required | Anonymous-capable; optional `Authorization: Bearer`, optional refresh cookie |
| Body | None (0 bytes; small body limit) | None |
| Success | 200 with the same `LoginUserResponse` shape (`userId`, `accessToken`, `tokenType`, `expiresAt`) in the ApiResponse envelope; new `Set-Cookie` | 204 No Content; `Set-Cookie` clearing `dp_refresh_token` (same Path, Secure, HttpOnly, SameSite) |
| Failure | 401 `Authentication.InvalidRefreshToken`, generic message, cookie cleared; 5xx for unexpected failures | 5xx only for unexpected failures |

Both responses send `Cache-Control: no-store` and `Pragma: no-cache`. Reuse the login response DTO for refresh rather than adding a near-duplicate.

## Test matrix
- **Positive:** login → refresh returns 200, a new access token works, and the new cookie differs from the old one with the same `Expires` deadline. Logout with a bearer → 204, cookie cleared, the old access token now gets 401 on a protected endpoint, and refresh with the old cookie gets 401.
- **Logout by cookie only:** an expired or absent bearer with a valid cookie → 204, and the session is revoked.
- **Idempotency:** repeated logout, logout with no credentials, a malformed cookie, or an already revoked or expired session → always 204, with no state change for other sessions.
- **Rotation:** reusing an old rotated cookie → 401 while the current session still refreshes (D-004). An expired fixed deadline → 401.
- **Race (PostgreSQL):** concurrent refresh and logout on one session. In every interleaving the session ends revoked, and after both complete no access or refresh token of that session works.
- **Isolation:** two users; logout by user A never affects user B's sessions. A second session of the same user stays active.
- **Inactive user:** refresh → 401.
- **Privacy:** response bodies and captured logs contain no refresh token; command `ToString` is redacted.
- **Gateway:** both routes are POST-only, forward cookies and `Set-Cookie`, enforce the body limit, and leave other private paths unpublished.
