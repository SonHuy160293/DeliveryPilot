## Behavior and invariants
- Normalize accepted email by trimming and using a consistent case-insensitive key compatible with the current PostgreSQL lower(PrimaryEmail) uniqueness rule. Proposed storage is invariant lowercase; test any non-ASCII equivalence against PostgreSQL and settle mismatches before release. DisplayName is trimmed. Password is never trimmed, normalized or persisted raw.
- A successful registration stages exactly one User and one credential row. An equivalent existing email must not change the existing display name, credential, status or other state.
- All staged rows commit through the existing command pipeline/IUnitOfWork, never SaveChangesAsync inside a repository or handler. Failed Results, exceptions and commit failures leave no partial registration.
- No tenant/project/approver grant is created or derived from a caller-supplied identifier. User identity remains platform-scoped and the Users integration contract remains compatible.
- Preserve Users and reliability/outbox state when migrating. Persist instants as UTC DateTimeOffset.

## Persistence contract (no HTTP surface)
**Reviewed implementation additions; not present before this task:**

| Model/operation | Implemented contract |
|---|---|
| PasswordCredential, shared.PasswordCredentials | UserId Guid primary key and required FK to shared.Users.Id, PasswordHash nonempty text containing only the versioned protected verifier, CreatedAt UTC DateTimeOffset. One row per user; Restrict deletion. No raw Password field or duplicate hash column on User. |
| PasswordCredential.Create(userId, passwordHash, createdAt) | Enforce nonempty user ID/hash and UTC creation semantics. A lightweight domain model may omit the shared audit base to avoid unrelated inherited columns. |
| IUserRepository.ExistsForRegistrationAsync(string normalizedEmail, CancellationToken) | Require the pipeline transaction, acquire a per-canonical-email transaction-scoped lock, then test lower(PrimaryEmail) equality using parameterized SQL. Staging AddAsync already exists. |
| IPasswordCredentialRepository.AddAsync(PasswordCredential, CancellationToken) | Stage in the same IdentityDbContext without committing. |

Reviewed race strategy: transaction-scoped PostgreSQL advisory locking keyed by the same canonical email as the database comparison, followed by a fresh read under the transaction's reviewed isolation. Example SQL design: SELECT pg_advisory_xact_lock(hashtextextended(lower(@email), 0)); then compare lower(PrimaryEmail). This is the selected new implementation design. Lock-key collisions may serialize unrelated requests but must not weaken database uniqueness. Retain the unique index as the final integrity guard; do not rely on a read-before-insert alone.

Handle a remaining commit-time DbUpdateException only when its PostgreSQL unique-violation code and constraint name identify UxUsersPrimaryEmailCi. After rollback/clearing tracking, translate it at the module transaction boundary to ConflictException("Registration.EmailExists", "This email is exist"). Unknown database exceptions must remain failures. The handler cannot catch every collision because the unit of work commits after it returns; coordinate this handoff with TASK-DP-002-002. A normal duplicate check may throw the same domain conflict before staging.
