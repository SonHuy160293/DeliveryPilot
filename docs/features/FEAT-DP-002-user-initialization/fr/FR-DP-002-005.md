# FR-DP-002-005 — Enforce authenticated-context validity

## Requirement statement
The system shall require a currently valid authenticated context for protected access and reject contexts that have expired or been ended under the reviewed session policy.

## Preconditions and trigger
A protected operation is attempted using an issued authentication context, including a replay or any supported continuation/refresh flow.

## Main behavior
Apply the reviewed validity rules consistently before granting access. Expiration or invalidation must not be bypassed by replaying the same proof or obtaining a continuation from an ended context. A user who needs to authenticate again receives a safe next step.

## Validation, business rules and authorization
NFR-002/NFR-004 apply. The user specified a 10-minute access JWT and a refresh token with a fixed 7-day maximum from login, with both lifetime values read from appsettings. There is no additional idle timeout or simultaneous-session count limit in this phase. Login and refresh deliver the refresh token via a Secure, HttpOnly cookie with SameSite and CSRF protections. Each successful refresh rotates the refresh token and the old token cannot be reused; rotation does not extend the original maximum. Reject an old rotated token without revoking its still-valid current session. Recheck account status on each protected request and refresh. Logout revokes the current session's refresh token and immediately rejects its already-issued access tokens; requests already admitted may finish. This draft does not choose a persistence model.

## Failure and edge cases
Test expired credentials, ended-context replay, concurrent continuation/logout and account-state changes as defined by policy. Authentication failure must not cause a protected business mutation; a known invalid context must not be accepted because a dependency is unavailable.

## Verification criteria
- A valid context is evaluated for resource permissions rather than automatically granted access.
- Expired and ended contexts fail protected access.
- Continuation cannot revive a context after the logout boundary defined by D-006.
- The configured access and refresh lifetimes are enforced; successful rotation invalidates the old refresh token.
- After logout, refresh proof in the selected scope cannot be used and already-issued access tokens in that scope are immediately rejected.
- Rotation never extends the fixed refresh-session deadline. Protected requests and refresh reject an account that is no longer active.
- Reuse of an old rotated refresh token fails without revoking the current valid session.

## Open questions
The implementation task specifies the atomic refresh/logout race, admission boundary and failure behavior needed to enforce the confirmed policy. The user-specified duration values must come from appsettings; no numeric policy for additional lifetimes is implied.
