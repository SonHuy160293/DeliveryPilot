# FR-DP-002-007 — Separate platform authentication from resource authority

## Requirement statement
The system shall keep platform registration/login separate from granting organization, project, client-sharing or artifact-approval permissions.

## Preconditions and trigger
A newly registered or authenticated user attempts to enter an organization, retrieve a project/artifact or perform an approval.

## Main behavior
Use the verified identity as input to the applicable resource authorization decision. Require authorized membership/sharing/approver scope from the owning feature. Registration/login must not implicitly create an organization or treat a claimed role, TenantId or client label as access authority.

## Validation, business rules and authorization
BR-002, BR-004, BR-005 and BR-008 apply: verified identity is not resource authority. Registration accepts no tenant, role or grant fields and creates no membership/project/approver authority. Future owning features define positive access grants.

## Failure and edge cases
An authenticated user without a grant must not access a resource by changing an identifier or tenant selection. An invited client authenticating successfully must still be denied unrelated resources and unauthorized approval actions.

## Verification criteria
- A registered identity receives no tenant/project/approver grant from registration alone.
- Login does not turn a TenantId, role claim supplied by a caller, or client label into permission.
- An authorized resource path remains subject to its owning feature's permission checks.

## Open questions
None for this negative authorization invariant. Detailed membership/sharing/approval policies remain owned by their separate features and are not prerequisites to storing a platform identity.
