# FR-DP-002-002 — Handle repeated or conflicting registrations safely

## Requirement statement
The system shall prevent registrations for the same reviewed canonical identity from creating competing identities or changing an existing account without proof of control.

## Preconditions and trigger
A registration is retried or submitted concurrently using a trim/case-equivalent email, including one already registered.

## Main behavior
Enforce platform-wide case-insensitive email uniqueness and at most one new identity/credential pair. Return duplicate feedback exactly "This email is exist"; the reviewed task transport uses Conflict. Never replace existing credentials, profile or activation state.

## Validation, business rules and authorization
Email is the confirmed identity key. Trim and use case-insensitive matching compatible with PostgreSQL lower(PrimaryEmail); protect the database constraint as the final concurrency guard. Explicit duplicate disclosure is the user-selected policy for this phase. No additional provider account-linking behavior is included.

## Failure and edge cases
Cover mixed formatting where the policy treats identifiers as equivalent, simultaneous submissions and retry after a lost response. Reject incompatible account-linking or takeover attempts; account merge/linking is outside this feature.

## Verification criteria
- Equivalent concurrent submissions commit one identity/credential pair.
- Every losing or repeated submission reports the reviewed duplicate conflict without mutating an existing account.
- Retry after uncertain success does not return another account's userId or replace its protected verifier.

## Open questions
None blocking registration. Tests must verify application/database equivalence for accepted non-ASCII email input rather than silently imposing a new identifier policy.
