# UR-DP-002-002 — Access the platform through a verified identity

## Problem and context
A returning agency user or external collaborator needs to prove control of their existing identity before accessing protected work. Successful authentication must remain distinct from organization, project and artifact authorization.

## User need
As a returning platform user, I need to sign in using the supported authentication method so that I can continue work under my own identity and only within my authorized scope.

## Business value and observable outcome
An eligible user can establish an authenticated context; an invalid proof or ineligible account cannot. Validate that users receive useful failure guidance without disclosure of another person's account information.

## Scope, constraints and exceptions
Covers login and the validity of the resulting authentication context. Membership and project selection belong to FEAT-DP-003/FEAT-DP-004. Authentication alone grants no tenant, project or approver permissions (BR-004, BR-005, BR-008; NFR-001, NFR-002). Federation, MFA and account recovery are not assumed to be MVP capabilities.

## Evidence and validation
The roadmap explicitly includes login and logout. Internal need-level review confirms the actor, outcome and resource/privacy boundaries. Registration uses email/password and does not issue a JWT; detailed session and logout behavior remains in separate draft FRs. This review is not authorization to implement those flows.

## Open questions
Functional details such as session duration, refresh, logout scope and post-login navigation are deferred to the associated FR/US review. They do not alter this user need or authorize their implementation.


## Readiness review — 2026-11-02
Reviewed for internal completeness against the confirmed registration phase and applicable global constraints. User clarification and subsequent confirmation in this conversation resolve public self-registration, immediate activation, no email verification and no automatic login. Ready denotes requirement completeness, not client approval; approval_ref remains null. Broader login/logout implementation contracts remain separate.
