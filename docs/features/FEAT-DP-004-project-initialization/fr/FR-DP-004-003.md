# FR-DP-004-003 — Capture the project brief and Product Goal

**Provenance:** Drafted 2026-11-09 with `dp-feature-engineer` from the roadmap, requirements, workflow discovery and [ADR-001](../../../architecture/adr-001-delivery-module-placement.md). Business choices marked **User-selected** were made by the user in the joint feature review on 2026-11-09 (see the decision record in [feature.md](../feature.md)). `ready` records internal completeness review for task planning, not client approval; `approval_ref` stays null and nothing here is implemented.

## Requirement statement
The system shall let participants with brief-edit permission record and update the brief (problem, objectives and success criteria, scope and exclusions, assumptions, constraints and dependencies, open questions) and the Product Goal, showing which items are still missing.

## Preconditions and trigger
A project the caller participates in with brief-edit permission per the project role matrix in FR-DP-004-005 (Project Administrator, PM, BA).

## Main behavior
Each item may be empty (each up to 4000 characters); the project shows which items are missing. Changes record actor and UTC time; previous Product Goal values stay in history.

## Validation, business rules and authorization
- Readiness policy, not a waterfall gate (workflow §5.1).
- Guests holding PM or BA have brief-edit as a work permission (OQ-004-06).

## Failure and edge cases
- Participant without brief-edit: rejected.
- Over-length item: rejected.
- Stale version: conflict.

## Verification criteria
- A new project shows all brief items as missing except name and purpose.
- Updating the Product Goal keeps the previous value in history.
- A Viewer or Developer cannot edit the brief.

Criteria are scenarios for task planning, not executed tests.
