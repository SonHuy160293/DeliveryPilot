# TASK-DP-004-008 — Issue, resend and cancel project guest invitations

## Objective and source contract
Let a Project Administrator or member PM invite an external person by email with any role except Project Administrator, resend with a rotated proof, cancel a pending invitation, and stage the invitation email for Notification. Sources: [FR-DP-004-008](../fr/FR-DP-004-008.md), [FR-DP-004-010](../fr/FR-DP-004-010.md); [US-DP-004-006](../us/US-DP-004-006.md) AC-001 and AC-004; [US-DP-004-008](../us/US-DP-004-008.md) AC-002; OQ-004-05/06/19; PRJ-11, PRJ-21. ## Behavior and invariants
- **Project access rule (defined in [TASK-DP-004-004](TASK-DP-004-004.md), reused here):** the caller needs an `Active` participant row for `(OrganizationId, ProjectId, UserId)`; otherwise 404. A `Member` participant must also pass `IWorkspaceAuthority.RequireAsync` for the workspace, uncached for commands; a denial is answered 404 and Identity being unavailable 503. A `Guest` needs no workspace membership. Permissions are the union of the caller's active roles under the FR-DP-004-005 matrix; guests never get cadence, participant, guest, client-PO, initialization or administrator permissions. A participant who lacks the needed permission gets 403.
- Commands check access and the required permission first, then lock the `Projects` row `FOR UPDATE` and recheck the caller's participation inside the transaction, so a concurrent removal or revocation wins (FR-DP-004-010).
- Every accepted change appends exactly one `project.ProjectEvents` row in the same transaction with actor, acting organization, UTC time, reason, `Details` (previous and new values) and the resulting `ProjectVersion`. A request that changes nothing appends no event.
- Stale `expectedVersion` gives 409 and no change. The pipeline transaction commits.
- Permission: invite-and-revoke-guests (Administrator or member PM; never a guest).
- One `Pending` invitation per project and normalized (trimmed, lower-case) email; a second issue for the same email gives 409. An email that already belongs to an active guest of the project is refused when known at acceptance, not at issue, because Projects cannot map emails to users.
- The proof is a random secret of at least 256 bits, shown to nobody in the API; only its 32-byte SHA-256 verifier is stored. `ExpiresAt = LastIssuedAt + 7 days`.
- **Resend:** new proof and verifier, new delivery row, `LastIssuedAt` and `ExpiresAt` restart; the old proof stops working. **Changing the offered role** is done by cancelling and issuing a new invitation, linked through `ReplacesInvitationId`.
- **Cancel:** status `Cancelled` with actor and time; the invitation can no longer be accepted.
- **Issuance limits** mirror Identity's defaults (`OrganizationInvitationIssuance`: 60-second cooldown and 10 per day per recipient, 100 per hour per scope), counted from `ProjectGuestInvitationDeliveries` per project and per recipient, configurable; exceeding gives 429.
- **Email staging:** in the same transaction, a `ProjectGuestInvitationEmailRequestedV1` is written to the outbox with the payload (recipient, project name, offered role, inviter display name, proof) envelope-encrypted with Notification's public key. The inviter's name comes from Identity's batch lookup at issue time and is not stored in Projects tables (PRJ-12, OQ-004-19). If the name lookup fails, the invitation is not issued (503).
- Events `invitation.issued`, `invitation.resent`, `invitation.cancelled`, with recipient email but never the proof or verifier.

## API contract (only for API tasks)
- **Route base (proposed):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/projects`. Not exposed through the Gateway until TASK-DP-004-017.
- **Authentication and tenant:** `[Authorize]`; user and session from `ICurrentUserProvider`; the workspace is the route `organizationId` and every query filters by it first (ADR-001 D-07).
- **Errors:** 400 validation; 401; 403 participant without the permission; 404 project of another workspace or caller not an active participant (same response); 409 conflict; 503 Identity unavailable.
- **Routes (proposed):**
  - `POST .../projects/{projectId:guid}/guest-invitations` (`email`, `role`);
  - `GET .../guest-invitations?status=pending`;
  - `POST .../guest-invitations/{invitationId:guid}/resend` (`expectedVersion`);
  - `POST .../guest-invitations/{invitationId:guid}/cancel` (`expectedVersion`, `reason`).
- **Success:** 201 on issue; the response never contains the proof.
- **Errors:** 400 invalid email or role `ProjectAdministrator`; 403 guest PM or missing permission; 409 pending invitation exists or stale version; 429 issuance limit; 503 Identity unavailable.

## Persistence, events and integrations
Writes invitations, deliveries, outbox message and event in one transaction. Configuration: Notification public key and producer options, mirroring Identity's `InvitationDeliveryProducerOptions`, `InvitationDeliveryStager` and `InvitationEmailEnvelopeFactory`.

## Test matrix
- **Issue:** pending invitation for the project only; one delivery row; one outbox message whose decrypted payload has the five fields.
- **Duplicate:** second pending invitation for the same email in the same project gives 409; the same email in another project succeeds.
- **Resend:** verifier changes; expiry restarts; a new delivery row and message exist.
- **Cancel:** status `Cancelled`.
- **Role:** `ProjectAdministrator` rejected.
- **Limits:** cooldown and daily limit give 429.
- **Permissions:** guest PM and Developer get 403.
- **Secrecy:** no proof or verifier in events, responses or captured logs; the outbox payload is ciphertext.
