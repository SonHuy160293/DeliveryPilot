# TASK-DP-004-009 — Track guest-invitation delivery and answer Notification eligibility checks

## Objective and source contract
Close the delivery loop for guest-invitation emails on the Projects side: publish requests, consume delivery status into `ProjectGuestInvitationDeliveries`, and answer Notification's eligibility check so cancelled, rotated or expired invitations are not emailed. Sources: [FR-DP-004-008](../fr/FR-DP-004-008.md); [US-DP-004-006](../us/US-DP-004-006.md) AC-001 and AC-004; [PRJ-21](../../../architecture/modules/projects/design-decisions.md#prj-21). All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

## Scope and dependencies
**In scope:** broker registrations for the two messages; status consumer in the Projects worker; eligibility endpoint in the Projects API with a dispatch-key filter; configuration and secret mount for the dispatch key.

**Out of scope:** Notification's side ([TASK-DP-004-001](TASK-DP-004-001.md)); invitation commands ([TASK-DP-004-008](TASK-DP-004-008.md)); publishing through the Gateway (the endpoint is internal and never published).

**Depends on:** [TASK-DP-004-008](TASK-DP-004-008.md) and [TASK-DP-004-001](TASK-DP-004-001.md).

## Behavior and invariants
- **Publish:** the outbox relay publishes `ProjectGuestInvitationEmailRequestedV1` to the entity name fixed in [TASK-DP-004-001](TASK-DP-004-001.md).
- **Status consumer:** validates the message, finds the delivery by `DeliveryMessageId`, and applies it only when `Sequence` is greater than `LastEventSequence`, so duplicates and out-of-order messages are harmless. It stores status and failure code and never changes the invitation's own status. Unknown deliveries are acknowledged and ignored.
- **Eligibility:** `Allowed = true` only when the delivery is the invitation's `CurrentDeliveryMessageId`, the invitation is `Pending` and not expired; then `ExpiresAt` is returned. Every other case, including an unknown ID, is `Allowed = false`. The endpoint reveals nothing else.
- The endpoint requires the dispatch key (constant-time comparison); a missing or wrong key gives 401, an unconfigured key 503. It is not behind bearer authentication and not published.
- No proof, recipient or payload in logs.

## Persistence, events and integrations

## Test matrix
- **Status:** queued, sent, failed with code, suppressed, expired and obsolete are stored; a lower or equal sequence is ignored; unknown delivery is ignored.
- **Eligibility:** current pending delivery → allowed with expiry; after resend the old delivery → not allowed; cancelled, accepted, declined, expired, unknown → not allowed.
- **Key:** missing or wrong key 401; unconfigured 503; bearer token alone is not accepted.
- **Broker (when available):** a staged request reaches the request exchange; a status message reaches the consumer.
- **Secrecy:** logs contain no recipient or proof.
