# TASK-DP-004-018 — Grant the Projects API runtime access to the project schema

## Objective and source contract
In a deployed stack, the Projects API account `projects_api` has no privileges on the `project` schema. That schema was added by [TASK-DP-004-002](TASK-DP-004-002.md) after the deployment grants were written in [TASK-DP-025-012](../../FEAT-DP-025-client-engagement/tasks/TASK-DP-025-012.md).
- Every request that touches `project.*` fails with "permission denied", which the API returns as **HTTP 500**.
- Since [TASK-DP-025-011](../../FEAT-DP-025-client-engagement/tasks/TASK-DP-025-011.md), that includes **engagement detail**, because it reads `project.Projects` for the summary tier and the projects section.
- It also includes every project route from TASK-DP-004-003 onwards.

This task restores least-privilege runtime access and proves it against a deployed stack.

Sources:
- [FR-DP-004-001](../fr/FR-DP-004-001.md): projects can be created and read.
- [FR-DP-025-006](../../FEAT-DP-025-client-engagement/fr/FR-DP-025-006.md): engagement detail and summary.
- NFR-002 (least privilege), NFR-003 (append-only history), NFR-005 (a deployed stack that works).

All of these are `ready` with `approval_ref: null`. This is a technical defect fix, so no User Story is invented.

**How it was found (2026-11-13):** during TASK-DP-004-001, the optional `scripts/Test-Deployment.ps1` stopped at "Engagement detail" with HTTP 500. The cause was confirmed by reading `deploy/setup/db-grants.sh`. Not yet reproduced on a deployed stack; reproducing it is step 1 below.

## Behavior and invariants
- After migrations, `db-grants.sh projects` gives `projects_api`:
  - `USAGE` on schema `project`;
  - `SELECT, INSERT, UPDATE, DELETE` on all its tables;
  - `USAGE, SELECT` on all its sequences.

  It mirrors the `engagement` block, inside an `IF EXISTS … nspname = 'project'` guard, so the script still works on a database migrated before `AddProjectPersistence`.
- **History stays append-only:** `REVOKE UPDATE, DELETE ON project."ProjectEvents" FROM projects_api` when the table exists. This matches `EngagementEvents` and the application's append-only guard.
- **No `CREATE` and no `TRUNCATE`** on `project` for `projects_api`; `projects_migrator` keeps ownership of every `project` table.
- **`projects_worker` gets nothing on `project`** in this task.
- The script stays idempotent: running it twice gives the same privileges.

## Persistence, events and integrations
- No migration, no schema change, no application change.
- Grants are refreshed by the existing compose `db-grants` step after the migration runner.
- Tables added to `project` by later migrations are covered the next time the step runs, because it uses `ALL TABLES IN SCHEMA`, as for `engagement`.
