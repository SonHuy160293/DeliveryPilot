## Behavior and invariants

- **Contract (proposed names):** `ProjectGuestInvitationEmailRequestedV1(MessageId, CorrelationId, CausationId, Producer, OrganizationId, ProjectId, InvitationId, IssuedAt, ExpiresAt, Payload)`; `EventType = "notification.project-guest-invitation-email-requested.v1"`, `TemplateId = "project-guest-invitation.v1"`, `Purpose = "projects.project-guest-invitation"`. `Validate()` requires producer `projects`, UUIDv7 message and invitation IDs, non-empty organization and project IDs, UTC times and `ExpiresAt > IssuedAt`. `AssociatedData()` binds message, correlation, causation, producer, purpose, template, organization, project and invitation IDs and both times, so a payload cannot be replayed under another project or invitation.
- **Payload** `ProjectGuestInvitationEmailData(Recipient, ProjectName, OfferedRoleName, InviterDisplayName, Proof)`, encrypted. The inviter's display name is supplied by Projects from Identity at issue time (OQ-004-19). No workspace name: Projects holds no copy of Identity's organization name (PRJ-12). `ToString()` redacts.
- **Status** `ProjectGuestInvitationEmailStatusV1` has the same shape, statuses and allowed failure codes as the organization status message, producer `notification`, monotonic `Sequence` per delivery.
- **Delivery rules equal the organization flow:** intake is idempotent by message ID; the job expires 5 minutes before `ExpiresAt`; suppression, retries and provider outcomes behave the same; every outcome stages one status message.
- **Eligibility before every send attempt:** `GET {ProjectsOrigin}/api/v1/integrations/project-guest-invitation-deliveries/{deliveryMessageId}/eligibility` with `X-Invitation-Dispatch-Key`, configured by `ProjectGuestInvitationDispatch:ProjectsOrigin` and `ProjectGuestInvitationDispatch:ApiKeyFile`. Response `InvitationDeliveryEligibility(Allowed, ExpiresAt)` as today. `true` sends; `false` marks the job obsolete and stages `obsolete`; any error, timeout, misconfiguration or invalid answer means "do not send now" and the job is retried later. A cancelled, rotated or expired invitation is therefore never emailed once Projects answers `false`.
- **Separate key:** the Projects dispatch key is a different secret from Identity's; neither module can ask the other's eligibility endpoint with it.
- The proof, recipient and rendered body never appear in logs, traces, status messages or exceptions.

## Test matrix

- **Contract:** valid message passes; wrong producer, non-v7 IDs, non-UTC times, expiry before issue fail; associated data changes when project or invitation ID changes; `ToString()` contains no proof or recipient.
- **Intake:** a valid message creates one job; a duplicate message ID creates none; a payload encrypted under another project's associated data fails to decrypt and is rejected without logging content.
- **Eligibility:** allowed → sent; not allowed → obsolete with status; timeout, 500, missing key file, bad origin and malformed JSON → not sent and retried; the Identity eligibility endpoint is never called for this kind and vice versa.
- **Delivery:** suppression, provider failure, retry and expiry each stage the matching status with an increasing sequence.
- **Operations and migration:** redrive and reconcile-accepted stage the new status type; migration permits the new kind while preserving the existing allowed kinds.
- **Rendering (Mailpit):** the email contains the project name, offered role, inviter's display name and an acceptance link with the proof, and no workspace name placeholder.
- **Regression:** all existing organization-invitation and verification tests pass unchanged.
- **Broker:** request and status messages route through the new entity names.
