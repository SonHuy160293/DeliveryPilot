# TASK-DP-004-017 — Publish project routes through the Gateway and verify the VS-02 journey

## Objective and source contract
Expose the project API through the Gateway with an explicit allowlist and run roadmap slice VS-02 end to end: record an engagement, create a project under it, invite the client PO as a guest, accept, assign and activate. Sources: [ADR-001](../../../architecture/adr-001-delivery-module-placement.md) §5 (Gateway row); [FR-DP-004-001](../fr/FR-DP-004-001.md), [FR-DP-004-007](../fr/FR-DP-004-007.md), [FR-DP-004-008](../fr/FR-DP-004-008.md); [US-DP-004-001](../us/US-DP-004-001.md), [US-DP-004-006](../us/US-DP-004-006.md), [US-DP-004-007](../us/US-DP-004-007.md), [US-DP-004-009](../us/US-DP-004-009.md). All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

## Codebase evidence
Verified 2026-11-10: `src/Gateway/DeliveryPilot.Gateway/proxy.json` has clusters `identity` and `notification` only, with one explicit route per path and method; `GatewayRequestMiddleware` lists `no-store` prefixes; `tests/DeliveryPilot.Gateway.Tests` asserts the allowlist; `scripts/Test-GatewayDeployment.ps1` checks deployed routes. The `projects` cluster and engagement routes are added by [TASK-DP-025-013](../../FEAT-DP-025-client-engagement/tasks/TASK-DP-025-013.md).

## Scope and dependencies
**In scope:** allowlisted routes for the project endpoints that exist in source when this task starts; CORS and `no-store` handling; route tests; the deployed VS-02 journey including a real invitation email in the local mail catcher.

**Out of scope:** internal endpoints (`integrations/...`), which stay unpublished; FEAT-DP-015 guest sharing.

**Depends on:** [TASK-DP-025-013](../../FEAT-DP-025-client-engagement/tasks/TASK-DP-025-013.md) for the `projects` cluster and deployed Projects API, and the API tasks [TASK-DP-004-003](TASK-DP-004-003.md)–[TASK-DP-004-016](TASK-DP-004-016.md). Take final paths from the controllers in source; the routes in those tasks are proposals.

## Behavior and invariants
- Public prefix `/projects/api/v1/...` as for engagements; no catch-all; GUID constraints kept; unlisted paths get the Gateway 404/405.
- The invitation response routes (`project-invitations/...`) and the guest list (`me/guest-projects`) are published; the eligibility endpoint is not.
- Project responses are `no-store`. The Gateway adds no authorization of its own.

## Persistence, events and integrations
None. Trace and correlation headers pass through (NFR-009).

## Executor handoff
Module `src/Gateway/DeliveryPilot.Gateway` and its tests. `implementation_skill` is null.

## Implementation plan
1. Routes in `proxy.json`; `no-store` prefixes.
2. Route tests.
3. Extend `scripts/Test-GatewayDeployment.ps1`; run the journey locally.

## Test matrix
- **Allowlist:** every published project route is forwarded; an unlisted path gives 404, a wrong method 405; `integrations/project-guest-invitation-deliveries` is not reachable.
- **Journey (deployed, local):** engagement → project under it → brief and Product Goal → add a PM → invite the client PO → email arrives with a working link → accept with the matching account → assign client PO → initialize → project Active.
- **Isolation (deployed):** a workspace member not on the project and a guest of another project get 404; the guest is absent from Identity's member list.
- **Regression:** existing Gateway tests pass.

- [ ] `ARCHITECTURE.md` lists the published project routes.
- [ ] No route is published for an endpoint that does not exist in source.
