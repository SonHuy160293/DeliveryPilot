# TASK-DP-004-013 — Maintain the project stakeholder register

## Objective and source contract
Let a Project Administrator or PM (member or guest) record stakeholders with responsibilities and decision areas, optionally linked to a participant, without granting access. Sources: [FR-DP-004-011](../fr/FR-DP-004-011.md); [US-DP-004-010](../us/US-DP-004-010.md); OQ-004-11. All source UR/FR/US are `ready` with `approval_ref: null`: complete for planning, not client-approved.

## Codebase evidence
Reviewed 2026-11-13 against `f38eefd` and the user's working-tree completion of TASK-DP-004-004:
- Group A delivered `ProjectsController`, `ProjectAccessEvaluator`, `ProjectReadStore` and `ProjectCreationStore`; TASK-DP-004-005 introduced `ProjectMutationService` and its store, extended by TASK-DP-004-006. Reuse these and `ProjectPermissions.EditStakeholders`.
- `ProjectStakeholder` and its EF mapping already exist with independent `Version`, a same-project composite participant FK, retirement fields and normalized-email storage. Extend its domain behavior and add tenant-scoped queries and mutations without a migration.
- For stakeholder edits and retirement, check access, acquire the project `FOR SHARE` then the stakeholder `FOR UPDATE`, and check access again after the locks. Creation takes the project share lock. Compare each entry's own version, never change the project version, and record the locked project's current version on the event. The pipeline owns commit; do not call `SaveChangesAsync`.
- Check optional participant links in application code for an active participant of the same project before storing. A bad link returns 409 and stores nothing; callers may then explicitly submit an unlinked entry. Guest register reads require `EditStakeholders`; all members may read it.
- Use redacted command/request representations and avoid application logging of stakeholder names or emails. Tests use `ProjectsPostgreSqlCollection` and `DELIVERYPILOT_TEST_PROJECTS_POSTGRES`.

## Behavior and invariants
- **Project access rule (defined in [TASK-DP-004-004](TASK-DP-004-004.md), reused here):** the caller needs an `Active` participant row for `(OrganizationId, ProjectId, UserId)`; otherwise 404. A `Member` participant must also pass `IWorkspaceAuthority.RequireAsync` for the workspace, uncached for commands; a denial is answered 404 and Identity being unavailable 503. A `Guest` needs no workspace membership. Permissions are the union of the caller's active roles under the FR-DP-004-005 matrix; guests never get cadence, participant, guest, client-PO, initialization or administrator permissions. A participant who lacks the needed permission gets 403.
- Commands check access and permission, lock the project `FOR SHARE` and, for an existing stakeholder, its row `FOR UPDATE`, then recheck participation after the locks (FR-DP-004-010).
- Every accepted change appends exactly one `project.ProjectEvents` row in the same transaction with actor, acting organization, UTC time, reason, `Details` (previous and new values) and the resulting `ProjectVersion`. A request that changes nothing appends no event.
- Stale `expectedVersion` gives 409 and no change. The pipeline transaction commits.
- Permission: edit-stakeholders (Administrator, PM; a guest PM has it as a work permission). Every member participant can read the register; a guest reads it only when holding PM (FEAT-DP-015 OQ-015-02). Sharing entries with other guests is FEAT-DP-015.
- Fields: name (1–200), side `Vendor` or `Client`, organization (≤200), responsibilities and decision areas (≤2000 each), optional email (stored normalized), optional `participantId`.
- A linked participant must be an active participant of the same project when linked; otherwise 409 and nothing is stored; the caller may explicitly create an unlinked entry instead. The link grants nothing (BR-004).
- Retire sets `RetiredAt`/`RetiredByUserId`; retired entries are excluded from the default list.
- Stakeholders use their own `expectedVersion`; the project share lock does not change the project version.
- Stakeholder names and emails are personal data and are not written to application logs (NFR-008).
- Events `stakeholder.added`, `stakeholder.changed`, `stakeholder.retired`.

## API contract (only for API tasks)
- **Route base (proposed):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/projects`. Not exposed through the Gateway until TASK-DP-004-017.
- **Authentication and tenant:** `[Authorize]`; user and session from `ICurrentUserProvider`; the workspace is the route `organizationId` and every query filters by it first (ADR-001 D-07).
- **Errors:** 400 validation; 401; 403 participant without the permission; 404 project of another workspace or caller not an active participant (same response); 409 conflict; 503 Identity unavailable.
- **Routes (proposed):** `GET` and `POST .../projects/{projectId:guid}/stakeholders`; `PUT .../stakeholders/{stakeholderId:guid}`; `POST .../stakeholders/{stakeholderId:guid}/retire`.
- **Errors:** 400 blank name, unknown side or invalid email; 403 without the permission; 404 stakeholder not in project; 409 link target not an active participant, or stale version.
