# TASK-DP-004-007 — Manage team participants and delegate project administration

## Objective and source contract
Let a Project Administrator or member PM add workspace members with roles, change their roles and remove them, and let a Project Administrator grant or give up `ProjectAdministrator`, never leaving the project without one. Sources: [FR-DP-004-005](../fr/FR-DP-004-005.md), [FR-DP-004-006](../fr/FR-DP-004-006.md), [FR-DP-004-013](../fr/FR-DP-004-013.md); [US-DP-004-004](../us/US-DP-004-004.md), [US-DP-004-005](../us/US-DP-004-005.md); [US-DP-004-012](../us/US-DP-004-012.md) AC-001 and AC-002; OQ-004-04/09/14; PRJ-04. ## Behavior and invariants
- **Project access rule (defined in [TASK-DP-004-004](TASK-DP-004-004.md), reused here):** the caller needs an `Active` participant row for `(OrganizationId, ProjectId, UserId)`; otherwise 404. A `Member` participant must also pass `IWorkspaceAuthority.RequireAsync` for the workspace, uncached for commands; a denial is answered 404 and Identity being unavailable 503. A `Guest` needs no workspace membership. Permissions are the union of the caller's active roles under the FR-DP-004-005 matrix; guests never get cadence, participant, guest, client-PO, initialization or administrator permissions. A participant who lacks the needed permission gets 403.
- Commands check access and the required permission first, then lock the `Projects` row `FOR UPDATE` and recheck the caller's participation inside the transaction, so a concurrent removal or revocation wins (FR-DP-004-010).
- Every accepted change appends exactly one `project.ProjectEvents` row in the same transaction with actor, acting organization, UTC time, reason, `Details` (previous and new values) and the resulting `ProjectVersion`. A request that changes nothing appends no event.
- Stale `expectedVersion` gives 409 and no change. The pipeline transaction commits.
- **Add:** the target must be an active member of the owning workspace (Identity batch membership check, uncached). A non-member is rejected with one generic error that reveals nothing about memberships elsewhere. At least one role is required.
- Adding a user who already has an ended row reactivates that row with fresh roles; earlier grants stay revoked (PRJ-04). Adding an active participant creates nothing.
- **Change roles:** replaces the set of non-administrator roles; unknown role names are rejected; the result must keep at least one active role.
- **Administrator role:** only a Project Administrator grants or removes `ProjectAdministrator`, only to or from a `Member` participant. Member PMs manage the other roles only.
- **Last administrator:** any command that would leave zero active administrator grants (step down, role removal, participant removal) is rejected with 409 `Project.LastAdministrator`. The count is taken under the `Projects` row lock, so two administrators removing each other concurrently leave at least one.
- **Remove:** sets status `Removed`, revokes active grants, records reason. The removed person is denied on the next request; their earlier actions keep their attribution.
- Events: `participant.added`, `participant.reactivated`, `participant.roles-changed`, `participant.removed`, `role.administrator-granted`, `role.administrator-removed`.

## API contract (only for API tasks)
- **Route base (proposed):** `api/v{version:apiVersion}/organizations/{organizationId:guid}/projects`. Not exposed through the Gateway until TASK-DP-004-017.
- **Authentication and tenant:** `[Authorize]`; user and session from `ICurrentUserProvider`; the workspace is the route `organizationId` and every query filters by it first (ADR-001 D-07).
- **Errors:** 400 validation; 401; 403 participant without the permission; 404 project of another workspace or caller not an active participant (same response); 409 conflict; 503 Identity unavailable.
- **Routes (proposed):**
  - `POST .../projects/{projectId:guid}/participants` (`userId`, `roles`);
  - `PUT .../participants/{participantId:guid}/roles` (`expectedVersion`, `roles`, `reason`);
  - `POST .../participants/{participantId:guid}/remove` (`expectedVersion`, `reason`);
  - `POST .../participants/{participantId:guid}/administrator/grant` and `.../administrator/remove` (`expectedVersion`, `reason`).
- **Errors:** 400 empty or unknown roles; 403 caller lacks the permission (Developer, guest PM, PM touching the administrator role); 404 participant not in this project; 409 last administrator, non-member target or stale version.

## Test matrix
- **Add:** Bob added as Developer and QA sees the project with both roles' permissions.
- **Non-member:** rejected generically. **Duplicate add:** no second row.
- **Rejoin:** a removed member re-added gets a reactivated row and only the new roles.
- **Remove:** Bob is denied on the next request; history keeps him as actor.
- **Last administrator:** removal and step-down rejected; after delegation the original administrator can step down.
- **Concurrent:** two administrators removing each other leave one; concurrent removal and role change give one consistent outcome.
- **Permissions:** Developer and guest PM get 403; a member PM cannot grant `ProjectAdministrator`; a guest can never receive it.
